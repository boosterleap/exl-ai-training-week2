Skills — packaged, invocable expertise

Week 2 Day 2's isolation spectrum named three levels: skills (in-context), subagents (isolated), agent teams (separate processes). This is the first one, in practice.

Concept: Skills — Packaged Expertise

The Big Picture

A skill is a set of specialized instructions that Claude Code loads when a task matches. Think of it as a recipe card: "when you see a review task, here's how to do it" or "when generating a visualization, follow these design principles."

Key point: Skills run in your current conversation context. Claude loads the skill's instructions, applies them to your task, and the results stay in your chat. No isolation, no separate session.

Skills vs. Slash Commands vs. Subagents — Choose Wisely

These three are related but different:

  • Slash command (Topic 03) — A fixed prompt template. You type /foo, you get a preset prompt run. Good for: templated workflows you type out frequently.
  • Skill — Instructions for how to do a particular kind of task, loaded automatically or on request. Claude recognizes when the task matches and applies the skill. Good for: quality standards (code review, visualization design), procedural checks (testing, linting), and recurring patterns that don't need to be user-triggered.
  • Subagent (Topic 05) — A completely isolated session, separate from your current chat. Good for: big, noisy tasks (running a test suite, searching a large codebase, training a model) that would clutter your main conversation.

Real-World Skill Examples

Claude Code comes with built-in skills already available to you:

  • dataviz — When you ask for a chart or visualization, this skill loads design principles (colors, accessibility, responsive layout) and ensures consistency across all your visualizations.
  • artifact-design — When you're about to create a web artifact, this skill gives guidance on structure, styling, interactivity.
  • security-review — When you run /code-review --security, this skill loads a security checklist: OWASP top 10, injection risks, auth patterns, etc.
  • simplify — When you ask Claude to clean up code, this skill checks for reuse, efficiency, and clarity — more thorough than a casual review.
  • update-config — When you're changing Claude Code settings, this skill understands the schema and helps you navigate permission modes, hooks, and environment variables.

When to Build a Custom Skill

You'd create your own skill when:

  • You have a repeating checklist or procedure that you want Claude to always follow. Example: "every time you review a PR, check for N+1 queries, missing error handling, and untested edge cases."
  • You want to enforce quality standards across your team without asking repeatedly. Example: "all visualizations use our brand color palette and are accessible to color-blind viewers."
  • You have a domain-specific task that benefits from specialized knowledge. Example: "when analyzing database performance, always check execution plans, index usage, and locking behavior."

Skill File Structure

Skills live under .claude/skills/ (project-scoped) or ~/.claude/skills/ (user-scoped). Each skill gets its own folder, and the folder name becomes the skill's identity on disk. Inside that folder, SKILL.md (exact filename, uppercase) is the one file that must exist:

.claude/skills/
├── my-code-review/
│   └── SKILL.md
├── my-visualization-standards/
│   └── SKILL.md
└── my-testing-checklist/
    ├── SKILL.md
    └── references/        # optional: extra docs, templates, scripts
        └── checklist-details.md

A SKILL.md file looks like:

---
name: my-code-review
description: Team's standard code review checklist
triggers: ["code review", "review the code", "examine changes"]
---

When reviewing code, check these in order:
1. **Correctness** - Does the logic work for all inputs?
2. **Safety** - Are there security issues?
3. **Performance** - Any N+1 queries, memory leaks?
4. **Testing** - Are edge cases covered?
5. **Style** - Does it match our CLAUDE.md conventions?

The frontmatter (name, description, triggers) is read for every skill up front, cheaply, so Claude Code knows what's available. The body below the frontmatter — and anything in an optional references/, scripts/, templates/, or assets/ subfolder — only loads once the skill is actually selected for use.

Built-in Skills Available to You

Run this in Claude Code to see all available skills:

/help

Look for the skills section. Built-in skills include dataviz, artifact-design, security-review, simplify, and more. You can load any of them explicitly or let them auto-load when appropriate.

Real-World Use Cases

1. Enforcing Code Style Across Reviews

The problem: Your team's code reviews are inconsistent. One reviewer checks for performance, another checks for security, another checks for style. Reviews take longer and catch different issues.

The solution: Create a skill team-code-review that loads a standardized checklist. When Claude reviews code, the skill ensures every review checks the same things.

The result: Consistent, thorough reviews. No more "wait, we should have caught that" in hindsight.

2. Visual Design Consistency

The problem: You're building charts and dashboards for a product. Without guidance, each one has different colors, fonts, and layouts. Inconsistent UX confuses users.

The solution: Create a skill visual-design-guide that loads your brand colors, accessible palettes, responsive layout principles. When you ask for a chart, the skill automatically applies.

The result: Every visualization looks like it belongs to the same product. No manual style enforcement needed.

3. Security Checklist Automation

The problem: Security vulnerabilities slip into production because security reviews are manual and error-prone. OWASP top 10 items like SQL injection, XSS, broken auth get missed.

The solution: Create a skill security-scan that checks for common vulnerabilities: injection risks, auth flaws, insecure defaults, etc. Run it before every code review.

The result: Vulnerabilities get caught earlier, in code review, not production.

4. Testing Coverage Verification

The problem: Features ship without proper test coverage. Later, a regression breaks production and catches you off guard. Coverage metrics exist but aren't enforced.

The solution: Create a skill test-coverage-check that asks about test cases for every code change, suggests missing tests, verifies edge cases.

The result: Testing becomes part of the code-writing process, not an afterthought.

5. Documentation Quality

The problem: APIs are shipped without documentation. New team members don't understand the interfaces. Support tickets ask "how do I use this?"

The solution: Create a skill api-documentation that ensures every function has a docstring with examples, parameters, return types, and error cases documented.

The result: APIs are self-documenting. Onboarding is faster.

Hands-on Practice: Five Examples

Example 1: List Available Skills

Claude Code chat panel

Step 1: Ask Claude to list all available skills:

Prompt
List all the skills you currently have available in this session. For each one,
tell me its name and a one-line description of what it's for.

What you'll see: A list of built-in skills (like dataviz, security-review, simplify) and any custom skills you've created. Each skill has a clear purpose.

Example output might include:

  • dataviz — Design guidance for charts, graphs, and visualizations
  • security-review — Security checklist for code review
  • simplify — Code simplification and refactoring guidance
  • artifact-design — Design principles for web artifacts
Checkpoint You know what skills are available. This is useful when you're about to ask for something that might benefit from a skill.

Example 2: Watch a Skill Be Used Automatically

Claude Code chat panel

Step 1: Ask Claude to create a visualization, which should trigger the dataviz skill automatically:

Prompt
Create a simple bar chart showing the top 5 countries by population.
Use appropriate colors and make it accessible. Tell me if a skill is being
applied and which one.

What's happening: Claude recognizes this is a visualization request. The dataviz skill loads automatically, bringing color palettes, accessibility guidelines, and responsive design principles into the response.

What you should see: The chart code should follow accessibility best practices (color contrast, labels, alt text). Claude should mention that it's using the dataviz skill.

Checkpoint You've seen a skill activate automatically. This is how skills save time—Claude recognizes the task type and applies the right expertise without you asking.

Example 3: Explicitly Invoke a Skill

Claude Code chat panel

Setup: Sometimes you want to explicitly tell Claude to use a particular skill, even if it wouldn't auto-trigger.

Step 1: Ask Claude to use a specific skill:

Prompt
Use the /simplify skill to review this Python function and suggest
improvements for clarity and efficiency:

def get_user(user_id):
    u = db.query("SELECT * FROM users WHERE id = ?", user_id)
    if u:
        return u[0]
    else:
        return None

What's happening: You're explicitly invoking the simplify skill. Claude applies its refactoring principles and returns cleaner, more Pythonic code.

Expected improvements:

  • Use proper variable names (not u, use user)
  • Use an ORM method instead of raw SQL
  • Simplify the conditional (use return u[0] if u else None)
  • Add type hints
Checkpoint The refactored code is clearer and more concise. You've explicitly triggered a skill.

Example 4: Create a Custom Skill

Claude Code chat panel

Setup: Create your own project-scoped skill for something you do repeatedly.

Step 1: Ask Claude to create a skill:

Prompt
Create a project-scoped skill folder at .claude/skills/code-review-checklist/
with a SKILL.md file that provides a detailed code review checklist. Include
checks for:
- Correctness (does the logic work?)
- Performance (any inefficiencies?)
- Security (injection risks, auth issues?)
- Testing (edge cases covered?)
- Documentation (is it clear?)

Show me the exact folder and file you created and explain how it would be triggered.

What's happening: Claude creates a folder .claude/skills/code-review-checklist/ containing a SKILL.md file with frontmatter (name, description, triggers) and the full checklist.

Step 2: Verify the folder and file exist:

# On Mac/Linux
ls -la .claude/skills/code-review-checklist/

# On Windows (PowerShell)
Get-ChildItem .\.claude\skills\code-review-checklist\
Checkpoint The skill folder exists with SKILL.md inside it — not a flat .md file directly under skills/.

Step 3: Now use it. Ask Claude to review some code and request the skill explicitly:

Prompt
Review this Python code and use the code-review-checklist skill:

def process_payment(user_id, amount):
    user = db.query(f"SELECT * FROM users WHERE id = {user_id}")
    if user:
        balance = user[0]['balance']
        if balance >= amount:
            balance -= amount
            db.execute(f"UPDATE users SET balance = {balance} WHERE id = {user_id}")
            return True
        return False
    return False

What you should see: Claude applies the checklist, catching several issues:

  • Security: SQL injection vulnerability (string interpolation instead of parameterized queries)
  • Correctness: Race condition (balance check and update aren't atomic)
  • Testing: What about insufficient balance? What about missing user?
  • Documentation: No docstring, unclear return type
Checkpoint Your skill was applied and the review was thorough and structured.

Example 5: Decide: Skill vs. Command vs. Subagent

Claude Code chat panel

Setup: You have a recurring workflow. Should it be a skill, custom command, or subagent?

Step 1: Describe your workflow and ask Claude to decide:

Prompt
I have this workflow I want to automate: Before any code goes to main,
I want to check if there are uncommitted changes, run the test suite,
check if the branch is up-to-date with main, and then verify the commit
message follows our conventions.

Should I implement this as:
1. A custom slash command (/pre-commit)?
2. A skill that runs automatically before edits?
3. A subagent that runs in isolation?

Explain why one is better than the others for this specific workflow.

What Claude should explain: This is a procedural check that should block actions—a skill is wrong (skills don't block). A slash command is good if you want to call it manually. A subagent is overkill for this. Best answer: a custom hook (Topic 06) that runs automatically, or a custom command you trigger explicitly before commits.

Key insight: The right tool depends on whether you want automatic enforcement (skill), manual triggers (command), or isolation (subagent).

Checkpoint You've thought through the differences and can now choose the right tool for your own workflows.
