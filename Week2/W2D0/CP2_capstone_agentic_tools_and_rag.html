Capstone Phase 2 — Agentic Tools & RAG

Phase 1 built the ground truth: a real database, four policy documents, and one deliberate gap. Phase 2 builds the assistant itself — a bounded tool-use loop (Day 1's agentic loop, run on your own Claude Code) that reads each inbound email, calls a small number of grounding tools, and drafts a reply that cites a specific record and a specific document. This is also where the gold_loan gap gets exercised for real: does the assistant escalate, or does it fabricate a policy?

Concept: Grounding tools + a bounded tool-use loop

Two tools, not one do-everything tool

Per CLAUDE.md's ground rules, this phase builds exactly two small, clearly-named tools:

  • get_loan_record(loan_id) — looks up the applicant + loan row, and reports a grounding_available flag plus which policy file (if any) governs this product. Mirrors W2D1/snippets/insurance_lookup_server.py's get_claim_and_policy exactly.
  • search_policy(query, product) — semantic search (sentence-transformer embeddings, cosine similarity) over the policy chunks, scoped to one product's document so a 4-document corpus doesn't return a plausible-but-wrong-product match.

The loop

A bounded (max 6 iterations) tool-use loop: send the email, let Claude call get_loan_record, then — only if grounding_available is true — search_policy, then produce a final JSON object: the drafted reply, whether the case was escalated, and which policy files were actually cited. The system prompt states the same ground rules as CLAUDE.md: never invent a term, always ground a claim in a tool result, and never state or imply a final approve/deny decision — that's reserved for a human underwriter, built in Phase 5.

Why product-scoped search matters

With only 4 short policy documents, an unscoped semantic search can return a plausible-looking chunk from the wrong product — e.g. a "surcharge" question about a rural home_loan case pulling back the personal_loan doc's dependents-surcharge section instead. Passing product (already known from get_loan_record) restricts the candidate set to that product's own document before scoring similarity.

Key Learning Objectives

By the end of Phase 2, you will:

  • Build a small, typed tool surface instead of one catch-all function
  • Wire a real bounded tool-use loop against the Claude API (not the Agent SDK harness — that's a deliberate contrast point for later topics)
  • Implement product-scoped semantic search over a small policy corpus
  • Verify — with real output, not a hope — that the assistant escalates instead of fabricating when grounding is unavailable
  • Parse a model's final answer defensively (models sometimes wrap requested JSON in reasoning prose despite being told not to)
