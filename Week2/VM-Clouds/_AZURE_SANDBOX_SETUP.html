Azure Sandbox Setup

Self-provision a standalone Azure OpenAI resource in your assigned sandbox subscription and connect to it using API-key authentication. Every learner runs this during Day 2 AM's framework-landscape topic — follow the numbered steps yourself in your own sandbox.

Scope note: this exercises Azure OpenAI's raw model-serving API directly (via the openai Python package) — it does not install or exercise the Microsoft Agent Framework orchestration SDK itself, which stays at awareness level this cohort. You're calling the model endpoint Agent Framework would sit on top of, not the framework itself.

On this page 1. Sandbox limits Where steps run 2. Create the resource 3. Deploy a model 4. Configure access 5. Verify once 6. Finish safely

1. Sandbox limits

The four-hour clock starts with the sandbox. Reserve the final 20 minutes, stop the sandbox when finished, and allow 15–20 minutes for automated cleanup.
  • Azure resources must remain in East US, East US 2, West US, or West US 2.
  • Global Standard, if used for the model deployment, is a processing type—not a resource region.
  • Use only the assigned subscription and pre-created resource group.

Where to complete each step

Three different places show up across this guide — know which is which:

  • Azure Cloud Shell (the >_ icon in portal.azure.com, or Cloud Shell reached from the sandbox) — verified live as the reliable place to run the Azure CLI commands in Step 3 (az login, list-models, deployment create). It's pre-authenticated to your sandbox identity, so no separate credential setup is needed there.
  • The Ubuntu VM — the standard place learners run the Step 5 verification script, alongside the rest of Week 2's work. Use the bash commands throughout this guide.
  • Your own local machine — this guide's troubleshooting was verified this way, but it's not the expected path for the session. Use the PowerShell commands on Windows, bash on macOS/Linux, if you do work here.

Open the repository in VS Code, use Terminal → New Terminal, and activate the environment first. Commands below are given for both shells — use whichever matches your terminal.

Ubuntu VM (bash)

conda activate ai_agent_env
cd /home/labuser/Desktop/Persistent_Folder/exl-ai-training-week2-claude
pwd

Windows (PowerShell)

conda activate ai_agent_env
cd D:\path\to\your\repo
pwd

Use the browser only for the training sandbox portal and Azure portal.

2. Create the resource (portal.azure.com)

Current as of July 2026: this is a five-minute self-serve step. You provision the resource yourself in the portal — no separate sandbox-administrator hand-off is needed for this simple path.
  1. In portal.azure.com, select Create a resource and search for Azure OpenAI. Microsoft now surfaces a consolidated "Foundry" resource ahead of it in search results — ignore that one; select the plain Azure OpenAI entry, then Create.
  2. Basics tab: Subscription = assigned sandbox subscription; Resource group = the pre-created sandbox group; Region = East US, East US 2, West US, or West US 2; Name = any descriptive name (e.g. exl-azure-openai-instance); Pricing tier = S0 (currently the only tier Azure offers for new resources).
  3. Network tab: All networks, including the internet, can access this resource is fine for this classroom exercise.
  4. Tags tab: leave empty.
  5. Review + create → Create. Once deployment finishes, select Go to resource.
Verified live, July 2026: creating the resource does NOT auto-deploy a model, despite what it may look like in the portal. az cognitiveservices account deployment list returns [] immediately after creation. Every call against the resource will 404 until you complete Step 3 below — don't skip it.

Naming note: Microsoft has been folding "Azure AI Foundry" branding into Microsoft Foundry (portal at ai.azure.com). A standalone Azure OpenAI resource like this one still supports plain API-key auth — no Foundry project is required for this exercise.

3. Deploy a model (Azure CLI — the reliable path)

Verified live, July 2026: skip hunting for a "Deployments" blade in the classic portal — it isn't there. Model deployment management moved to the Foundry portal (ai.azure.com) and, on some resources, isn't exposed in the classic portal.azure.com resource blade at all (Resource Management only shows Keys and Endpoint, Encryption, Resource Upgrade, Pricing tier, Networking, Identity — no Deployments item). The Azure CLI works every time and doesn't depend on which portal layout you land on.

Default to Azure Cloud Shell (browser-based, no local install) via the >_ icon in the top bar of portal.azure.com — it's authenticated automatically to your sandbox identity, and it's what was used to verify every command below. Only use a locally-installed Azure CLI if you specifically need to (Cloud Shell covers this exercise fully):

az login
az account list --output table

Step 3a — list models actually available to this resource (don't guess a model/version — quota and region availability vary):

az cognitiveservices account list-models --name YOUR-RESOURCE-NAME --resource-group YOUR-RESOURCE-GROUP --output table

Pick a row where LifecycleStatus is GenerallyAvailable — rows marked Deprecating/Deprecated still list, but Azure rejects new deployments against them. For a cheap, fast, one-off classroom call, prefer a small "mini"/"nano" tier chat model over a full flagship model.

Step 3b — create the deployment:

az cognitiveservices account deployment create --name YOUR-RESOURCE-NAME --resource-group YOUR-RESOURCE-GROUP --deployment-name class-mini --model-name MODEL_NAME_FROM_LIST --model-version "MODEL_VERSION_FROM_LIST" --model-format OpenAI --sku-capacity "1" --sku-name "GlobalStandard"
Verified live, July 2026: --sku-name "Standard" was rejected for a current model with (InvalidResourceProperties) The specified SKU 'Standard' of account deployment is not supported by this model. Newer models are often only offered via GlobalStandard — try that first for anything recent. (Per the sandbox rules in Step 1, Global Standard is a processing type, not a region violation — the resource itself stays in your allowed region regardless.)

Step 3c — confirm it stuck:

az cognitiveservices account deployment list --name YOUR-RESOURCE-NAME --resource-group YOUR-RESOURCE-GROUP --output table
Verified live, July 2026 — a naming trap to avoid: Azure uses "Deployments" for two unrelated things. The Resource Group → Deployments blade shows ARM provisioning history (auto-named things like OpenAICreate-20260721030442 from when you created the resource) — that is not a model deployment name and will 404 on every API call if used as one. The value you actually want is the --deployment-name you chose in Step 3b (e.g. class-mini), confirmed in the Step 3c listing.

Bash line-continuation is \; PowerShell's is the backtick ` — they are not interchangeable. If in doubt, keep the command on one line, which works in both.

4. Configure API-key access

The sandboxes are separate. Signing in to the Azure portal does not authenticate the Ubuntu VM. Get the key and endpoint from the resource's Keys and Endpoint blade (classic portal), and use the exact --deployment-name you set in Step 3b (e.g. class-mini) — not anything from a Resource Group "Deployments" list. Set these directly in your own terminal session — never in a file committed to the shared repo.

Ubuntu VM (bash)

read -rsp "Azure OpenAI API key: " AZURE_OPENAI_API_KEY; echo
export AZURE_OPENAI_API_KEY
export AZURE_OPENAI_ENDPOINT="https://YOUR-RESOURCE-NAME.openai.azure.com/"
export AZURE_OPENAI_DEPLOYMENT="YOUR-DEPLOYMENT-NAME"

Windows (PowerShell)

$secureKey = Read-Host "Azure OpenAI API key" -AsSecureString
$env:AZURE_OPENAI_API_KEY = [System.Net.NetworkCredential]::new('', $secureKey).Password
$env:AZURE_OPENAI_ENDPOINT = "https://YOUR-RESOURCE-NAME.openai.azure.com/"
$env:AZURE_OPENAI_DEPLOYMENT = "YOUR-DEPLOYMENT-NAME"
  • Paste Key 1 (or Key 2) at the prompt, and use the exact Endpoint and deployment name. The deployment value is the deployment name you chose, not necessarily the underlying model name.
  • Once the key/endpoint/deployment are set, running the actual chat completion does not require Azure CLI or az login — CLI was only needed in Step 3 to create the deployment, since the portal path for that was unreliable.
  • PowerShell's read equivalent is Read-Host — bash's read -rsp has no direct PowerShell counterpart, so the command shape differs even though the intent (masked, non-history input) is the same.
Keep the key secret. Never print it, paste it into chat/screenshots, or commit it to any file. Report an exposed key immediately so an administrator can rotate it.

5. Run one bounded verification, via Claude Code

The script already exists at W2D2/snippets/azure_openai_verify.py — reads the three environment variables from Step 4, makes exactly one chat-completions call, and prints the result. Rather than pasting Python into the terminal yourself, open the Claude Code chat panel (Ubuntu VM, ai_agent_env conda environment, alongside the rest of Week 2's work) and prompt it directly:

Run W2D2/snippets/azure_openai_verify.py and show me the result.
If it errors, show me the exact error — don't guess at a fix without it.

The script reads from os.environ rather than shell-interpolating values, so it behaves identically regardless of which shell Claude Code runs it in. api_version='2024-10-21' (set inside the script) is confirmed working (GA, not preview) as of July 2026 — confirm against current docs if it's since aged out.

Verified live, July 2026 — two model-tier gotchas:
  • max_tokens is rejected on newer models (gpt-5-family and later) with Unsupported parameter: 'max_tokens' is not supported with this model. Use 'max_completion_tokens' instead. — the script uses max_completion_tokens already, for exactly this reason.
  • Reasoning-tier models spend part of the completion budget on hidden reasoning_tokens before producing visible text — a low max_completion_tokens (e.g. 60, even 300) can silently return empty content with finish_reason: 'stop' and no error, since reasoning tokens alone can exceed a tight budget before any visible text is written. The script's 600 leaves comfortable headroom for a one-sentence answer; check resp.usage.completion_tokens_details.reasoning_tokens if output ever looks blank.
  • On Windows, printing the response can raise UnicodeEncodeError: 'charmap' codec can't encode character... — the model's answer often contains characters (curly quotes, non-breaking hyphens) that Windows' legacy console codepage can't render, even though the API call itself succeeded. The script forces UTF-8 stdout to avoid this; if you see this error, the auth/deployment are fine — it's a print-time issue only.
Prompt note: avoid asking bare "what is Microsoft Agent Framework?" — verified live, models answer about the old, unrelated 1990s/2000s "Microsoft Agent" animated-character Windows SDK (Clippy-era), not the 2025+ AI agent orchestration framework this course means. The script's prompt disambiguates by date and description instead of relying on the bare product name.

Stop after one successful response; this is a demo, not a loop.

What this confirms. The Azure OpenAI resource is wired end-to-end — authenticate, hit a real deployment, get a real completion back. That's the full extent of this exercise: a bounded connectivity check, not a build-out.

Scope: this call goes through the openai package straight to Azure OpenAI's model-serving API — it does not touch the Microsoft Agent Framework orchestration SDK itself (not installed this cohort, awareness-level only). You've called the model endpoint Agent Framework would sit on top of, not the framework.

Worth noticing: how much of getting this working was on you by hand — the exact deployment name (not the ARM provisioning name), the SKU type, and even the parameter name changing between model generations (max_tokens → max_completion_tokens). Compare that to how little Claude Code/Claude Agent SDK exposes you to at this same layer.

Need configuration details? Check the training portal first, then the assigned resource in the Azure portal. For missing resources, deployments, keys, quota, or permissions, contact the sandbox administrator.

6. Finish safely

Only run the last step once you're done needing the resource. Clearing env vars, an optional az logout, and checking git status are all safe to do any time — none of them touch the resource. Stopping the sandbox is different: it triggers automatic cleanup that deletes every resource in it, including the one you just deployed. Do that step last, once nothing later in the session still needs this resource.

The sandbox's four-hour clock started when it launched, not when you started using it. Check the training portal for time actually remaining against how much of the session you still need it for, and stop it (or extend it, if the platform allows) accordingly.

  1. Stop any running script that can call the endpoint.
  2. Clear the shell values you set:

    Ubuntu VM (bash)

    unset AZURE_OPENAI_API_KEY AZURE_OPENAI_ENDPOINT AZURE_OPENAI_DEPLOYMENT

    Windows (PowerShell)

    Remove-Item Env:AZURE_OPENAI_API_KEY, Env:AZURE_OPENAI_ENDPOINT, Env:AZURE_OPENAI_DEPLOYMENT
  3. If you separately used Azure CLI outside Cloud Shell, run az logout. Not needed for the API-key exercise itself, and not needed for Cloud Shell (its session ends on its own).
  4. Confirm nothing was committed — git status --short in the repo before closing.
  5. Once you no longer need the resource for anything else this session: stop the sandbox before the four-hour deadline and allow 15–20 minutes for cleanup. Manually deleting the resource first isn't necessary — stopping the sandbox deletes everything in it automatically.
Done means: callers stopped, shell credentials cleared, optional CLI session logged out, secrets uncommitted, and — only when the resource is truly no longer needed — sandbox stopped.
