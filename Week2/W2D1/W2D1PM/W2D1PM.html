Topic 01 · The Claude Agent SDK

1query() vs ClaudeSDKClient — seen through the app built on them~25 min

Concept. The SDK gives two shapes: query() is one-shot — send a prompt, get a response, session ends. ClaudeSDKClient is a persistent connection — you keep a conversation, tool state, and permission context alive across many turns. Every conversation you've been having in the Claude Code panel all week is a ClaudeSDKClient-shaped session: it persists context, remembers tool results from three turns ago, and keeps running until you end it.

  • When real code would actually use each shape. query() fits a one-off automation script — e.g. a nightly job that classifies overnight emails and exits. ClaudeSDKClient fits anything interactive or multi-step where later turns depend on earlier ones — exactly what an operations assistant needs.
  • What "ending a session" actually clears. It clears working context and any live tool/permission state for that conversation. It does not clear CLAUDE.md or anything already written to disk — those are project-level, read fresh by the very next session.
  • Why Claude Code is obviously client-shaped, not query-shaped. A one-shot call couldn't have remembered your Topic 03 tool design from this morning, couldn't reference a file you read four turns ago, and couldn't keep a running plan across a 70-minute build — all things you're about to rely on this session.

Instructor drives live, variation A — a brand-new session. Claude Code chat panel — start a brand new session (not a resumed one) and ask it directly:

Prompt
Explain, from the inside: are you currently running as a one-shot query or
as a persistent client session? What evidence would show the difference —
what do you retain between my messages that a one-shot call wouldn't?
Debrief Point at: it remembers your Topic 01–06 work from this morning if you're in the same long-running session, it can reference a tool result from several turns back, and it maintains a coherent plan across turns — all persistent-client behavior, not one-shot query behavior.

Instructor drives live, variation B — three-way memory comparison. Open three things side by side if your setup allows it (or run them one after another): (1) this morning's original AM session if it's still open, (2) a claude --resume of that same session from a fresh terminal, (3) a brand-new session. Ask all three the identical question:

Prompt — run identically in all three
What is the very first claim_id we discussed together, if anything?
Debrief The original/resumed session should answer correctly from conversation memory. The brand-new session should have no idea — unless you already wrote that fact into CLAUDE.md, in which case it might mention it from the artifact layer, not from "remembering." Distinguishing those two sources of a correct-sounding answer is the whole point of this comparison.

Learners repeat. Open a second, separate Claude Code session (new terminal tab or new window) and ask it the same question yourself — confirm it has no memory of anything from your first session (aside from CLAUDE.md).

Topic 02 · Built-in & custom tools

2Build a real in-process MCP tool — then a second one, on the same server~70 min

Concept. Claude Code ships with built-in tools (Read, Write, Bash, web fetch, ...) out of the box. Custom domain tools are added via MCP servers — in Claude Code's case, an in-process (stdio) server it launches itself as a subprocess, with each tool addressable as mcp__<server>__<tool>. This is exactly the tool you designed on paper in this morning's Topic 03.

  • One server, many tools. A single MCP server process can expose several tools — you're about to add a second tool to the same server rather than standing up a whole new process, which is the normal pattern for a related family of lookups.
  • How Claude Code chooses between multiple available tools. It reads each tool's name and description and picks based on what the current request actually needs — a good tool description is part of the contract, not an afterthought.

Build it together — first tool. Claude Code chat panel — have Claude Code write the server, don't hand-copy the reference file yet:

.FastMCP, stdio transport. It should expose one tool, get_claim_and_policy
(claim_id: str), that:
  1. Looks up the claim in data/insurance/claims.db (tables: claims,
     policies; join on policy_id)
  2. Uses the product -> policy-doc-prefix mapping in data/_DATA_README.md
     to find matching files under data/insurance/policies/
  3. Returns a validated pydantic model including a grounding_available
     boolean, true only if a matching policy doc file exists
Put it at W2D1/my_insurance_lookup_server.py. Then show me how to
register it in .mcp.json at the repo root.

Topic 03 · Structured outputs & message blocks

3Reading TextBlock / ToolUseBlock / ToolResultBlock / ThinkingBlock~25 min

Concept. Under the hood, every Claude Code turn is a sequence of typed message blocks: TextBlock (prose), ToolUseBlock (a tool call with validated arguments), ToolResultBlock (what came back), and optionally ThinkingBlock (visible extended reasoning). The pydantic model your MCP tool returns in Topic 02 is exactly what ends up inside a ToolResultBlock.

  • Streaming, in a real application. In a live app these blocks typically arrive incrementally as the model produces them, not all at once at the end — Claude Code's live-updating transcript is exactly that stream rendered for you.
  • Thinking vs. text. A ThinkingBlock is the model's own visible deliberation, shown separately from its actual reply (TextBlock) — useful for debugging why it did something, not meant to be the final answer itself.

Instructor drives live, variation A — narrate the blocks. Claude Code chat panel — ask Claude Code to call the tool again, but this time narrate its own message structure:

Prompt
Call get_claim_and_policy for claim CLM-424063. Then describe, in terms of
message blocks, what just happened: what was your ToolUseBlock's
arguments, what came back in the ToolResultBlock, and what — if anything —
did you reason about before or after in a way that would be a
TextBlock/ThinkingBlock?
Debrief If your Claude Code plan/model shows a visible thinking section, point at it directly as the ThinkingBlock. Emphasize the output your MCP tool returned is validated pydantic data, not free text — that's why it can slot cleanly into a ToolResultBlock the model can trust.

Instructor drives live, variation B — call it twice, check idempotency. Call the exact same tool with the exact same argument twice in a row:

Prompt — repeat call
Call get_claim_and_policy for claim CLM-424063 again, a second time. Are
the two ToolResultBlocks identical? Did calling it twice cause any side
effect, or was it safe to repeat?
Debrief This should be a clean, boring "yes, identical, no side effect" — that's what idempotent looks like in practice, and it's exactly why this was safe to demonstrate live twice, unlike the write-tool contract discussed this morning.

Learners repeat. Deliberately call your tool with two different bad inputs — an empty string, and something the wrong shape entirely (e.g. a number instead of a claim ID) — and read how each error surfaces through the message blocks. Is it a clean ToolResultBlock error both times, or does one crash the tool?

Topic 04 · Memory & sessions

4session_id resume, CLAUDE.md, context compaction~40 min

Concept. Two different memory mechanisms, easy to conflate: session resume (continuing one specific conversation later via its session_id) and project context (CLAUDE.md/AGENTS.md, loaded fresh into every new session regardless of which one it is). Long sessions also trigger automatic context compaction — older turns get summarized so the session can keep going without hitting a context limit.

  • AGENTS.md as an emerging shared standard. Some tools look for CLAUDE.md specifically; AGENTS.md is an emerging cross-tool convention for the same idea — project context any agentic coding tool should read, not just one vendor's.
  • Compaction is automatic and lossy by design. You don't request it — it triggers as context fills, and it trades detail for space. That's exactly why anything you'll need later, in a different session or after heavy compaction, belongs in an artifact, not just in the conversation.

Instructor drives live, variation A — resume and recall. VS Code terminal — find your current session and resume it explicitly:

claude --resume
# or, if you know the session id:
claude --resume <session_id>

Ask the resumed session a question that only makes sense if it remembers earlier work:

Prompt (in the resumed session)
Without re-reading any files, tell me: what claim_id did we look up
together earlier this session, and what did get_claim_and_policy return
for it?
Debrief Contrast this with Topic 01's brand-new session, which had none of this. Then ask explicitly: "has this session's context been compacted at any point?" — discuss what that implies about trusting a very early instruction in a very long-running session.

Instructor drives live, variation B — interrupt mid-task, then resume. Start a small multi-step task, deliberately stop partway through (close the terminal or end the session), then resume it:

Prompt — start a multi-step task, then interrupt it
Look up claims CLM-424063, CLM-748422, and CLM-988147 one at a time, and
after each one tell me whether it needs escalation. Start with the first
one now.

After the first result, end the session, then claude --resume it back and ask:

Prompt — after resuming
Continue exactly where we left off — which claim comes next?
Debrief A resumed session should pick the task back up correctly. Compare this recoverability against what a brand-new session would do with the same instruction (it would have to start over from claim 1) — that's the practical value of session resume over relying on CLAUDE.md alone.

Topic 05 · Permissions & model choice

5Real permission modes, a real approval gate, Sonnet vs Opus~35 min

Concept. allowed_tools/permission rules decide what Claude Code may do without asking — but that's a pre-approval list, not a substitute for authorization logic inside a sensitive tool itself. Approval prompts exist for exactly the actions you haven't pre-approved. Model choice is a separate lever: Opus for reasoning depth on hard judgment calls, Sonnet for speed on routine ones.

  • Three states, not two. A permission rule can allow (never ask), ask (prompt every time), or deny (never allowed, no prompt at all) — you're about to see all three behave differently on the same tool.
  • Model choice interacts with judgment-heavy tasks. The ungrounded-claim refusal from this morning is exactly the kind of case where a deeper-reasoning model's extra care can matter — a faster model optimized for routine throughput may need an explicit instruction to double-check before answering.

Configure it together. Repo root, VS Code file explorer — create .claude/settings.json (or edit it if Claude Code already made one). A worked example is at snippets/settings_example.json — read it together, then adapt it rather than copy it blind: understand what each of allow/ask/deny does before saving.

Pitfall Putting a sensitive action in allow means Claude Code never asks before doing it — that's appropriate for a read-only lookup tool, not for anything that writes, sends, or approves something on a customer's behalf. Keep writes in ask (or fully in deny for this exercise) and enforce the real authorization check inside the tool's own code, not just the permission file.

Variation A — trigger a real approval prompt. Trigger a real approval prompt on purpose:

Prompt
Draft a reply to claim CLM-424063's customer and write it to
outputs/day1_draft_reply.md.
Checkpoint You should see a real permission prompt for the Write tool (since it's in ask, not allow). Approve it once, watch the file get created, then discuss: what would change if Write were in allow instead?

Variation B — now try deny. Temporarily move your MCP lookup tool into deny in .claude/settings.json, restart the session, and try to use it:

Prompt — with the tool denied
Call get_claim_and_policy for claim CLM-597471.
Debrief — all three states now observed allow = silent and immediate (Topic 02's original setup). ask = a real prompt you had to approve (variation A). deny = refused outright, no prompt, no path around it. Move the tool back to allow (or its original setting) before continuing.

Model choice. If your Claude Code setup lets you switch models (check /model or the model picker), run the fraud-tip claim (CLM-255335) once on the faster model and once on the deeper-reasoning model, and compare how each handles the ungrounded-policy situation from this morning's Topic 06.

Topic 06 · Cost awareness

6Reading your own session's real token/cost usage~15 min

Concept. Every Claude Code session tracks token-weighted cost as you go — this isn't a metering system you build, it's already reporting on the session you've been running all afternoon.

  • What actually drives the number up. Input tokens (everything read into context — including a large file read in full), output tokens (everything generated, including a long narrated explanation), and each additional tool round-trip all add up. A verbose "narrate everything" prompt like several you used earlier today costs more than a terse one that just asks for the answer.

Do this, variation A. Claude Code chat panel or CLI — check your session's own usage:

/cost

or ask directly in the chat panel:

Prompt
Summarize this session's token and cost usage so far, broken down if you
can by which turns were the most expensive (likely the MCP tool-building
turns vs. the short lookup calls).

Do this, variation B — quantify the verbose-vs-terse gap. Run the same lookup two ways and compare the cost delta directly:

Prompt 1 — verbose
Call get_claim_and_policy for CLM-597471 and narrate, in full detail,
every single field of the result and what it means.
Prompt 2 — terse
Call get_claim_and_policy for CLM-597471. Reply with one short sentence:
covered or not, and why.
Checkpoint You should be able to name a real, non-trivial difference between the two costs — a concrete number, not a guess. Note it down — Day 4 revisits this same idea (cost/perf) at the level of a whole eval suite, not just one session.

App build (19:00–19:30) · Day 1 of the progressive insurance app

Everything above was topic-scoped practice. This slot is different: it's the first increment of one continuous pipeline you'll keep extending every PM this week — resolve_email(email_id), an insurance capstone thread distinct from the logistics transfer exercise below. Today it does the smallest useful thing: read one inbound email, look up its claim and policy through Topic 02's stdio MCP tool, and either draft a grounded reply or escalate rather than guess.

AppBuild resolve_email(email_id) for one FNOL (First Notice of Loss) email~20 min
Claude Code chat panel

Direct Claude Code to build your own file — do not overwrite anything under app/:

Prompt
Create app/my_day1_resolve.py with a function resolve_email(email_id: str)
that:
1. Reads data/insurance/fnol_emails.csv and finds the row with this email_id.
2. Takes its claim_number_ground_truth column. If it's empty, return a result
   with found=False, escalate=True, and an escalate_reason explaining there's
   no claim number to look up -- do not call the lookup tool at all.
3. Otherwise call the insurance-lookup MCP tool's get_claim_and_policy(claim_id)
   (the same tool you built in Topic 02 this afternoon) to fetch the claim and
   policy.
4. If the lookup's grounding_available field is false, return found=True,
   escalate=True, draft_reply=None, and an escalate_reason saying no policy
   document exists for that product -- never draft a coverage statement
   without a grounding document.
5. Otherwise return escalate=False and a draft_reply naming the claim ID,
   policy ID, named insured, claim status, route_queue, and which policy
   document(s) it's grounded on.
Print the result as JSON when run with an email_id argument, e.g.
python -m app.my_day1_resolve CLN-001.
AppPredict, then verify, on three real emails~7 min

Before running anything, predict out loud which of these three will escalate and why, then run each through your resolve_email and check yourself:

  • CLN-001 — has a claim number.
  • CLN-003 — has a claim number, product commercial_package.
  • CLN-007 — an inquiry-category email.
Prompt
Run app/my_day1_resolve.py for CLN-001, then CLN-003, then CLN-007, and show
me each JSON result.
Checkpoint CLN-001 resolves to claim CLM-424063, grounded on the homeowners policy docs (POL-HOME-010_flood_rider.md and POL-HOME-010_water.md), with escalate: false and a real draft_reply. CLN-003 resolves to claim CLM-255335, product commercial_package — the deliberate no-policy-doc gap — so grounding_available: false, escalate: true, draft_reply: null. CLN-007 has no claim number at all, so found: false, escalate: true — a different kind of escalation than CLN-003's (nothing to look up, versus looked-up-but-ungrounded). If your output disagrees with any of these, that's the bug to chase before moving on.
