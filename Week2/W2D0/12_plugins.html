Plugins — packaging skills/commands/agents for distribution

Concept: Plugins — Packaged Extensions

The Big Picture

A plugin bundles together everything you've built so far (skills, commands, agents, hooks, even MCP server definitions) into one installable unit. Instead of each teammate manually copying `.claude/` files, they run claude plugin install my-awesome-plugin and get everything.

Why Plugins Matter

  • Shareable expertise: You've built a great code-review skill. Instead of explaining how to set it up, distribute it as a plugin.
  • Team onboarding: New teammate joins. Install three plugins, and they have all your team's conventions, commands, and tools. No manual setup.
  • Version control: Plugin versions are tracked. When you improve a skill, bump the version. Teams can upgrade when ready.
  • Distribution: Share publicly via marketplace, or privately within your org.

Plugin Structure

The manifest lives inside a .claude-plugin/ folder, but every component folder (skills/, commands/, agents/, hooks/) sits at the plugin root, not inside .claude-plugin/. Each skill keeps the same folder-per-skill + SKILL.md convention as standalone skills (Topic 04) — just nested one level deeper under skills/:

my-plugin/
├── .claude-plugin/
│   └── plugin.json     # Metadata: name, version, description
├── skills/              # Skills (from Topic 04) — one folder per skill
│   └── code-review/
│       └── SKILL.md
├── commands/            # Commands (from Topic 03) — flat .md files, no per-command folder
│   └── deploy.md
├── agents/              # Subagent specs (from Topic 05)
└── hooks/               # Hook scripts (from Topic 06)
    └── hooks.json

Installation Sources

  • Public marketplace: `claude plugin install name@marketplace-name` (e.g. `claude plugin install formatter@claude-plugins-official`) — official plugins
  • GitHub (or any git host): two steps — register the marketplace, then install a plugin from it: `claude plugin marketplace add user/repo` followed by `claude plugin install plugin-name@repo`
  • Local (development/testing, no install step): `claude --plugin-dir ./path/to/plugin`

Real-World Use Cases

1. Team Onboarding at Scale

The problem: Your team has 10 engineers. Each needs to install 3 tools, learn 5 custom commands, understand 2 subagents. Manual setup takes 4 hours per person.

The solution: One plugin bundles it all. Onboarding is `claude plugin install my-team-toolkit`.

The result: 30 minutes of setup instead of 4 hours per person. Scaling works.

2. Publish Expertise Publicly

The problem: You've built an amazing test-generation skill. Other teams would love it but don't know about it.

The solution: Publish it as a plugin on the Claude Code marketplace.

The result: Your tool helps the broader community. You gain recognition for the contribution.

3. Compliance and Standards

The problem: Your company has security standards (linting rules, audit hooks, policy checks) that must apply everywhere.

The solution: Corporate plugin with hooks that enforce these standards automatically.

The result: Every Claude Code session, everywhere in your org, enforces compliance.

4. Industry-Specific Tools

The problem: You work in fintech. You've built tools for PII redaction, regulatory checks, audit trails.

The solution: Package as a fintech plugin. Other fintech companies can install and use.

The result: Your tools become a distributed best practice in your industry.

5. Local Development Environment Consistency

The problem: Different developers have different setups. One uses Haiku, one uses Opus. One has hooks, one doesn't.

The solution: Dev environment plugin that sets up standard config for everyone.

The result: Consistent behavior across the team. No surprises when code changes hands.

Hands-on Practice: Two Examples

Example 1: List Installed Plugins

Terminal/PowerShell

Step 1: Check what's currently installed:

claude plugin list

What you'll see: List of installed plugins (if any). Initially likely empty.

Checkpoint You know the command to view plugins.

Example 2: Scaffold Your Own Plugin

Terminal/PowerShell

Step 1: Create a plugin scaffold:

claude plugin init w2d0-test-plugin

Step 2: Explore the structure Claude created. Note: claude plugin init scaffolds into your skills directory, not a plugins/ folder:

# On Mac/Linux
find ~/.claude/skills/w2d0-test-plugin -type f

# On Windows (PowerShell)
Get-ChildItem $env:USERPROFILE\.claude\skills\w2d0-test-plugin -Recurse

Step 3: Validate the plugin:

claude plugin validate ~/.claude/skills/w2d0-test-plugin

What you should see: "Valid" status indicating the plugin is correctly structured.

Checkpoint You've created and validated a plugin. You could add skills, commands, and agents to it.
