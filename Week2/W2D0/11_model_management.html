Model management — switching, fallback, and cost visibility

Concept

Model choice is a per-session (or per-task) dial, not a one-time setup decision. Claude Code exposes it as a setting (~/.claude/settings.json's "model" key), a CLI flag, and an in-session switch.

  • Depth vs. speed, the same tradeoff from Week 2 Day 1. A deeper-reasoning model costs more and is slower per turn; a faster one is cheaper but may need more explicit guidance on hard judgment calls.
  • Fallback exists for reliability, not just preference. --fallback-model lets a session automatically retry on a different model if the primary is overloaded or unavailable — a real production concern, not a hypothetical.
  • Cost is visible, not hidden. The same /cost-style reporting you used all through Week 2 works here too — check it before assuming a workflow is cheap.

Hands-on

1Check your current default
VM · terminal 
cat ~/.claude/settings.json | grep -i model || echo "no explicit model set — using the account default"
2Compare two models on the same task
Claude Code chat panel

If your setup lets you switch models mid-session (check your model picker or /model), give both the same genuinely ambiguous task:

Prompt
Here's a deliberately underspecified request: "make the config better."
Without asking me a clarifying question, tell me what you'd actually do
and why. (Run this once per model you're comparing.)
Checkpoint Compare: did the faster model barrel ahead with an assumption, while the deeper one flagged the ambiguity or asked first? Neither is universally "better" — it's a task-fit decision.
3Read your own cost
/cost
