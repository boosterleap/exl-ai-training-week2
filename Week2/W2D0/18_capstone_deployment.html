Capstone Stage 5 — Deployment

Stages 1-4 gave you a data-prep script, a trained model, a Streamlit UI, and a green pytest suite proving all three still work together. Everything so far has run directly on your VM, inside your own Python environment. In this final stage you package it into a container image that runs the same way anywhere Docker runs — no "works on my machine," no separately-installed dependencies, one artifact that carries the model and the app together.

Concept

  • A container ships the model and the UI as one unit, not two things that have to stay in sync. A bare Python script assumes whoever runs it already has the right interpreter, the right package versions, and the right trained model file sitting nearby. A container image bundles all of that — code, dependencies, and the model artifact — into something you can hand to anyone (or any server) and it just runs, identically, every time.
  • Baking the model in at build time is a deliberate choice, not the only option. The Dockerfile runs data_prep.py and train_model.py during the image build, so the trained model is already inside the image before it ever starts. The tradeoff: the image is bigger and a retrain means a rebuild, but the container never needs live internet access or training compute at runtime — it just serves. The update cycle becomes explicit and repeatable: retrain → rebuild → redeploy, not "hope the container can reach the data source when it boots."
  • A non-root user is baseline hygiene, not an exotic hardening step. By default a container runs as root, which means a compromised or buggy process inside it has root-level reach inside that container. Creating an unprivileged appuser and switching to it with USER appuser before the app runs costs one line and closes off a whole class of unnecessary risk — it's a habit worth having even for a training exercise like this one.
  • A healthcheck lets Docker (and anything orchestrating it) know the app is actually serving, not just that the process is alive. Streamlit exposes its own /_stcore/health endpoint for exactly this. HEALTHCHECK CMD curl --fail http://localhost:8501/_stcore/health || exit 1 polls it periodically — a process that's technically running but wedged will show up as unhealthy instead of silently looking fine.
Honesty note Every other reference file in this capstone was actually run and its output quoted in the guide. This one is different, and you should know that going in. The reference Dockerfile in W2D0/capstone/ was written by the course author but not build-tested — there was no Docker daemon available on the authoring machine. It follows a standard, well-established pattern (slim base image, non-root user, model baked in at build time), so there's good reason to expect it works, but "should work" and "verified" are not the same claim, and this guide won't pretend otherwise. Your VM has Docker confirmed installed and running, so when you build this for real in the next section, that build is the first actual verification this Dockerfile has ever had. If something in it needs fixing, that's the exercise working as intended, not a sign you did something wrong.

Hands-on

1Have Claude Code build the Dockerfile and requirements.txt
Claude Code chat panel
Prompt
I want to containerize my California Housing capstone at W2D0/capstone/ for
deployment. Create W2D0/capstone/requirements.txt and W2D0/capstone/Dockerfile.

requirements.txt should pin the libraries this project actually uses: pandas,
numpy, scikit-learn, matplotlib, seaborn, joblib, streamlit, pytest -- with
sensible minimum versions, not exact pins.

Dockerfile should:
- start FROM python:3.12-slim
- set a working directory, copy requirements.txt in, and pip install it
  before copying any application code (so dependency layers cache separately
  from code changes)
- copy data_prep.py, train_model.py, and app.py in
- bake the trained model into the image at BUILD time by running
  `python data_prep.py && python train_model.py` as a RUN step -- the
  container should never need to fetch data or train a model at runtime
- create a non-root user and switch to it before the app runs
- EXPOSE 8501 and add a HEALTHCHECK against Streamlit's own
  /_stcore/health endpoint
- ENTRYPOINT that runs `streamlit run app.py` bound to 0.0.0.0:8501 so it's
  reachable from outside the container

Explain each section as you write it so I understand why it's ordered the
way it is, not just what it does.
2Build the image for real — this is the actual verification
VM terminal

This Dockerfile has never been built before. Running the build here is not a formality on top of already-verified instructions — it is the test. Watch the build log; if a step fails, that's real information, not noise to scroll past.

Command
cd W2D0/capstone
docker build -t housing-capstone .

Pay attention to the RUN python data_prep.py && python train_model.py step in particular — that's the line doing the real work of baking the model into the image, and it's the step most likely to surface something the Dockerfile got wrong (a missing dependency, a path assumption, an ordering issue). If it fails, describe the error to Claude Code and have it fix the Dockerfile, then rebuild.

3Run the container and confirm it works
VM terminal
Command
docker run -p 8501:8501 housing-capstone

Open http://localhost:8501 in a browser, move a slider, click predict, and confirm you get a real prediction back — the same UI from Stage 3, now running entirely inside the container with no local Python environment involved. That end-to-end path, from a cold docker build to a working prediction in the browser, is what turns "the Dockerfile looks reasonable" into "the Dockerfile works."

If you want an extra gate before you'd call this deployable, this is also where Stage 4's test suite earns its keep: run pytest W2D0/capstone/test_capstone.py -v against the same project before you build the image, so you know the data, model, and UI were already sound going in. A container faithfully packages whatever you hand it — it doesn't fix a broken pipeline, it just ships it more conveniently.

Checkpoint docker build completes without error, docker run starts the container and Streamlit is reachable at http://localhost:8501, and moving a slider and clicking predict inside the browser returns a real prediction from the model baked into the image — not a cached page, not an error trace.
Reference files (only if the build gets stuck)

Reference files are at capstone/Dockerfile and capstone/requirements.txt — a standard pattern, but genuinely unverified until you (or your VM) build it. Treat your own build as the real test, not this file.

Capstone complete

Five stages, one public dataset, one continuous thread: you took California Housing through exploratory data analysis, trained and evaluated a model against a numeric quality floor, wrapped it in a Streamlit UI, locked it down with an automated test suite, and packaged the whole thing into a container image you built and ran yourself. At every stage, Claude Code did the building — you directed it, read what it produced, and used the reference files only for comparison when something needed checking, never as a starting point to copy from.

That's the whole point of this course: the skill isn't any single script, it's knowing how to direct an agent through a real, multi-stage build and verify each stage before trusting the next one. If you want to revisit any topic that fed into this capstone, the W2D0 index is the place to start.
