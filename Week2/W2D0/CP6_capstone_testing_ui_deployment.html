Capstone Phase 6 — Testing, UI & Deployment

Five phases built a grounded, multi-agent, guarded, governed loan-servicing assistant. Phase 6 closes the loop: a pytest suite that gates every quality floor this project has built up, a small Streamlit review queue a real loan officer would actually click through, and a container image — packaged honestly, including the one part of this phase that could not be verified on this machine.

Concept: Prove it, don't just build it

One suite, every floor

Each phase set its own quality bar: Phase 1's data shape, Phase 2/3's escalation-and-citation correctness, Phase 4's injection-scanner floor, Phase 5's audit-chain integrity and the fraud case's disposition. Phase 6 doesn't invent new checks — it collects all of them into one pytest run with clear failure messages telling you which earlier phase's script to re-run if something's missing.

A headless UI test catches what unit tests miss

The data can be sound and the eval gate can pass and the Streamlit app can still crash on load, or a button can silently do nothing. streamlit.testing.v1.AppTest runs the actual app script in a simulated session — no browser, no human clicking — and asserts on real widget state: title, button count, and (this project's own real bug, caught during this build) whether a cached SQLite connection survives Streamlit's rerun threading model.

Never bake a secret into an image

The static grounding data (the dataset, the policy docs) can be baked into the image at build time — it needs network access but no credential. The live pipeline needs ANTHROPIC_API_KEY, and that is never baked in; it's supplied at docker run time and the container's entrypoint runs the pipeline once, on first start, if it hasn't already.

Honesty about what got verified

Every other reference file in this capstone was run for real and its output quoted here. The Dockerfile is the one exception on this particular authoring machine — there is no Docker daemon available here, so it follows a standard pattern (slim base image, dependency-then-code layering, non-root user, a stdlib healthcheck) but has not itself been built. If your VM has Docker, your build is the first real verification this Dockerfile has ever had.

Key Learning Objectives

By the end of Phase 6 — and this capstone — you will:

  • Consolidate every phase's quality floor into one pytest suite with actionable failure messages
  • Smoke-test a Streamlit app headlessly, and find (and fix) a real cross-thread SQLite bug that only a rerun-aware test surfaces
  • Wire a review UI to a governance layer you built two phases ago, not a mock
  • Package a project honestly, including saying plainly what you could not verify
  • Have completed a full end-to-end agentic build: grounded data → tools + RAG → multi-agent + MCP → guardrails + memory + cache → HITL + observability + eval → tests + UI + deployment

3Smoke-test it headlessly, then run it for real
Claude Code chat panel
Prompt
Use streamlit.testing.v1.AppTest to load W2D0/capstone/app.py, run it,
assert no exception, assert the title, and assert 2 buttons per queued
case. Then click one Approve button and re-run, asserting still no
exception. Show me any exception in full if one occurs.
Predict first governance.ApprovalQueue opens its SQLite connection once, then Streamlit's testing harness caches and reruns the app. Do you expect a plain sqlite3.connect(...) to survive being reused across a rerun, or do you expect a specific, nameable error?
Debrief It does not survive by default — the real reference build hit exactly this: ProgrammingError: SQLite objects created in a thread can only be used in that same thread, because Streamlit's rerun model can hand a cached resource to a different thread than the one that created it. The fix is one keyword argument, sqlite3.connect(db_path, check_same_thread=False) — but you only find out you need it by actually running the interaction, not by reading the code and assuming it's fine. That's the entire argument for a headless UI test over "the code looks right."

Honesty note On the machine that authored this guide, there was no Docker daemon available, so the Dockerfile above was written but not build-tested — unlike every other file in this capstone, which was actually run and its real output quoted in these six phases. It follows a standard, defensible pattern, so there's good reason to expect it works, but "should work" and "verified" are different claims. If your environment has Docker, your build is the first real test this file has ever had — treat a failure there as the exercise working as intended, not a sign you did something wrong.

Capstone complete

Six phases, one real public dataset, one continuous thread: you took a real, messy 491-row loan dataset through grounded tool-use and RAG, split it into a multi-agent system served over a real network MCP protocol, hardened it with PII redaction, injection scanning, durable memory, and a semantic cache, gated every sensitive disposition behind a human-approval queue backed by a tamper-evident audit chain, watched a real eval gate score something short of perfect and understood why that's the right target, and closed with a tested UI and an honestly-packaged container. At every stage, Claude Code did the building — you directed it, read what it produced, and used the reference files only for comparison, never as a starting point to copy from.

That's the same lesson the whole of Week 2 has been making with the insurance and logistics threads, now in your own hands end to end: the skill isn't any single script, it's directing an agent through a real, multi-phase build and verifying each phase before trusting the next one.
