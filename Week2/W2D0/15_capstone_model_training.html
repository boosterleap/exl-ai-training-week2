Capstone Stage 2 — Model Training

Stage 1 gave you a clean outputs/housing.parquet and a feel for which features move the target. Now you turn Claude Code loose on the actual modeling: train a simple baseline, train something stronger, compare them honestly, and persist the winner plus its scores so later stages can consume them without re-running anything.

Concept

  • Always start with a baseline. LinearRegression is fast, has no hyperparameters to tune, and gives you a number to beat. If a fancier model can't clear that bar, the extra complexity isn't earning its keep. Training a baseline first isn't busywork — it's the control in the experiment.
  • MAE and R2 tell you different things — report both. Mean Absolute Error is in the target's own units (here, $100,000s), so it reads as "on average, how far off is a prediction" — easy to explain to a non-technical stakeholder. R2 is unitless and tells you what fraction of the variance in house values the model actually explains, which is what you want when comparing model architectures against each other. A model can look fine on one metric and mediocre on the other, so pick the winner on the metric your grading rule cares about (here, MAE), but log both.
  • Why random forests tend to beat linear regression on this dataset: housing prices don't move linearly with latitude/longitude — coastal proximity, local price clusters, and non-linear interactions between rooms/income/location are exactly the kind of structure a tree ensemble can carve up with splits, and a linear model can't represent no matter how well it's fit.
  • Persist metrics as structured JSON, not print statements. A print statement is for you, right now, reading a terminal. A metrics.json file is for every future consumer of this pipeline — Stage 3's Streamlit app wants to display the score, and Stage 4 will write an automated test that loads this file and asserts a quality floor on it. If the numbers only ever existed in scrollback, none of that downstream automation is possible.
  • Unit gotcha worth remembering now: MedHouseVal, the target column, is expressed in units of $100,000s (a value of 2.05 means a $205,000 home). Your model's raw predictions will be in the same units — Stage 3's UI multiplies by 100 to show a human-readable "$204.9k". If you see a prediction like 2.05 printed with no context later, this is why.

Hands-on

1Have Claude Code build the training script
Claude Code chat panel
Prompt
In W2D0/capstone, write a script called my_train_model.py that:
1. Loads outputs/housing.parquet (produced by Stage 1's data prep script)
2. Splits it into train/test sets (80/20, use a fixed random_state so it's
   reproducible) using MedHouseVal as the target and the other columns as
   features
3. Trains two models for comparison: a plain LinearRegression baseline, and
   a RandomForestRegressor(n_estimators=200, max_depth=12)
4. Evaluates both on the test set with MAE (mean absolute error) and R2,
   and prints a comparison table showing which one wins
5. Picks the model with the lower MAE as the winner
6. Saves the winning model to outputs/model.joblib with joblib
7. Writes outputs/metrics.json containing the MAE and R2 for BOTH models
   plus a "best_model" key naming which one won -- something like
   {"best_model": "random_forest", "linear_regression": {"mae": ..., "r2": ...},
   "random_forest": {"mae": ..., "r2": ...}}

Don't overwrite anything in capstone/ that already exists -- this is a new
file, my_train_model.py.
2Predict before you run
Your own judgment call
Before you run the script, write down a guess: which model do you expect to win, LinearRegression or RandomForestRegressor, and why? Think about what geographic features like latitude/longitude actually mean for house prices — is that relationship a straight line?
3Run it and compare against the real numbers
VM terminal
Run
uv run python W2D0/capstone/my_train_model.py

Check your printed MAE/R2 against the verified reference run: LinearRegression → MAE=0.5332, R2=0.5758. RandomForestRegressor → MAE=0.3456, R2=0.7921. Random Forest wins on both metrics — lower error, higher explained variance. If your script's numbers are close to these (exact values can drift slightly depending on train/test split randomness), your predict-then-verify guess was testable and you now know why: the forest can model the non-linear geography effect that a straight line fundamentally cannot.
