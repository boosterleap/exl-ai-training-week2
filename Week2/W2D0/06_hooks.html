Hooks — deterministic code at lifecycle events

A hook is your own code running at a fixed point in Claude Code's loop — not a suggestion in a prompt, an actual guarantee.

Concept: Hooks — Deterministic Automation

The Big Picture

A hook is code that Claude Code runs automatically at specific lifecycle events. Example events:

  • PreToolUse — Before any tool is called (Read, Edit, Bash, etc.)
  • PostToolUse — After any tool completes
  • SessionStart / SessionEnd — When a session begins or ends
  • UserPromptSubmit — When you press enter to submit a prompt
  • Stop / SubagentStop — When Claude stops generating or a subagent finishes
  • PostToolBatch — After a batch of parallel tool calls all resolve (this project's real .claude/settings.json uses this one to print a token-usage summary)

These aren't the only events — Claude Code also has hooks for session-lifecycle edges, subagent start, file/config changes, and more — but the ones above are the ones you'll reach for most often.

Key point: Hooks are deterministic. They run every time, unconditionally. No human judgment, no context pressure — just code that executes.

PreToolUse vs. PostToolUse

PreToolUse: Runs before the tool call happens. You have the tool name and parameters, but no result yet. Good for:

  • Blocking dangerous commands (e.g., "don't allow `rm -rf`")
  • Logging what tools are about to be called
  • Validating parameters before execution
  • Adding metadata or context to the call

PostToolUse: Runs after the tool completes and you have the actual result. Good for:

  • Logging what happened (with actual results)
  • Redacting sensitive information from results
  • Validating the result shape or contents
  • Augmenting the result (adding context, timestamps)
  • Triggering side effects (saving to database, alerting)

Hook Configuration in settings.json

Hooks are defined in .claude/settings.json. Each event name maps to an array of matcher groups, and each matcher group runs one or more hook handlers:

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/pre_tool_hook.sh"
          }
        ]
      }
    ],
    "PostToolUse": [
      {
        "matcher": "Read",
        "hooks": [
          { "type": "command", "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/post_tool_hook.sh" }
        ]
      }
    ],
    "SessionStart": [
      {
        "matcher": "",
        "hooks": [
          { "type": "command", "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/session_start.sh" }
        ]
      }
    ],
    "UserPromptSubmit": [
      {
        "matcher": "",
        "hooks": [
          { "type": "command", "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/validate_prompt.sh" }
        ]
      }
    ]
  }
}

For each level:

  • matcher — Filters which occurrences of the event trigger this group. For tool events this is a tool name (or regex, e.g. "Edit|Write" or "mcp__.*"); leave it "" (or omit) to match every occurrence. This project's real .claude/settings.json uses exactly this shape — see the PreToolUse → matcher: "Bash" entry there.
  • hooks — An array of handlers to run for that matcher. The most common type is "command", which runs a shell command; other types (http, mcp_tool, prompt, agent) exist for more advanced setups.
  • command — The shell command or script to execute. ${CLAUDE_PROJECT_DIR} expands to the project root so the path works regardless of your current directory.

How blocking actually works: there's no onFailure setting. A command hook communicates its decision through its exit code and, optionally, JSON printed to stdout:

  • Exit 0 — success; if the script printed JSON to stdout, Claude Code parses it for an explicit decision, otherwise execution just continues.
  • Exit 2 — blocking error; stderr is treated as the reason and the action is blocked (only PreToolUse, UserPromptSubmit, Stop, and SubagentStop can actually block this way — PostToolUse/SessionStart/SessionEnd cannot, since the tool has already run or there's no action to stop).
  • Any other exit code — non-blocking error; the transcript shows the hook failed, but execution continues.

For PreToolUse specifically, a script can instead print structured JSON like {"hookSpecificOutput": {"hookEventName": "PreToolUse", "permissionDecision": "deny", "permissionDecisionReason": "..."}} to deny (or allow) the call with a reason, instead of relying on the exit code.

How hooks receive data: command hooks get a JSON payload on stdin — not CLI arguments and not custom environment variables — containing fields like session_id, hook_event_name, and (for tool events) tool_name/tool_input. A script reads it with something like jq -r '.tool_input.command' < /dev/stdin. The only environment variables Claude Code itself sets for hooks are things like CLAUDE_PROJECT_DIR (project root) — always prefer stdin JSON for tool call details.

Hook Type Example Use What It Does
PreToolUse Prevent accidental deletion Block any Bash command with "rm -rf" before it runs
PreToolUse Audit tool usage Log every tool call with timestamp and parameters
PostToolUse Redact secrets Remove API keys and passwords from tool results before Claude sees them
PostToolUse Trace analysis After file reads, store them in a local trace database
SessionStart Setup automation Activate a Python virtual environment before the session starts
UserPromptSubmit Input validation Check that prompts don't contain accidental secrets before submitting

Real-World Use Cases

1. Audit and Compliance Logging

The problem: You're in a regulated industry. You need a complete audit trail: who ran what tools, when, with what inputs and outputs.

The solution: A PreToolUse hook that logs every tool call (tool name, parameters, timestamp) to a file. A PostToolUse hook that logs the result (status, result size).

The result: Complete, deterministic audit log. No human judgment, no missing entries. Compliance requirement satisfied.

2. Secret Redaction

The problem: A developer accidentally includes an API key in a config file. When Claude reads it, the key shows up in the chat and potentially in logs.

The solution: A PostToolUse hook that scans all Read results for patterns that look like secrets (AWS keys, tokens, passwords) and redacts them before Claude sees them.

The result: Secrets are never exposed. Claude sees "[REDACTED]" instead of actual keys.

3. Dangerous Command Protection

The problem: `rm -rf /` is one mistake away. You want a safety net.

The solution: A PreToolUse hook that blocks any Bash command matching dangerous patterns (rm -rf, > /dev/sda, DROP TABLE, etc.) before execution.

The result: Catastrophic mistakes are prevented. Claude can propose anything, but the hook enforces the safety boundary.

4. Automatic Testing Before Every Commit

The problem: Code gets committed without running tests. Broken tests reach CI/CD, wasting time.

The solution: A UserPromptSubmit hook that, if your prompt mentions "commit," automatically runs your test suite before proceeding. If tests fail, block the commit.

The result: Tests run automatically before any commit suggestion. You can't accidentally skip testing.

5. Environment Setup and Cleanup

The problem: Each session needs to activate a Python venv, load environment variables, connect to a database. Manual setup is error-prone.

The solution: A SessionStart hook that runs setup.sh (activates venv, loads .env, checks database connection). A SessionEnd hook that cleans up (closes DB, saves logs).

The result: Setup and cleanup happen automatically every session. No manual steps. No forgotten cleanup.

Hands-on Practice: Five Examples

Example 1: Create a Simple Logging Hook

Claude Code chat panel

Step 1: Ask Claude to add a PreToolUse logging hook:

Prompt
Add a PreToolUse hook to .claude/settings.json that logs every tool call.
Create a simple script that appends a JSON line to W2D0/outputs/tool_calls.jsonl
with format: {timestamp: "ISO8601", tool: "ToolName", action: "pre_use"}.

Show me the hook config and the script.

Step 2: Make sure the output directory exists:

# On Mac/Linux
mkdir -p W2D0/outputs

# On Windows (PowerShell)
New-Item -ItemType Directory -Path W2D0\outputs -Force

Step 3: Trigger a tool call to activate the hook. Ask Claude to read a file:

Prompt
Read the CLAUDE.md file and tell me the first three bullet points you see.

Step 4: Check the log file:

# On Mac/Linux
cat W2D0/outputs/tool_calls.jsonl

# On Windows (PowerShell)
Get-Content W2D0\outputs\tool_calls.jsonl

What you should see: A JSON line with your Read tool call logged, including timestamp and tool name.

Checkpoint The hook ran deterministically, without you asking for it. Every tool call is logged.

Example 2: Add a PostToolUse Hook

Claude Code chat panel

Step 1: Ask Claude to add a complementary PostToolUse hook:

Prompt
Add a PostToolUse hook to .claude/settings.json that, for Read tool results,
appends additional data: {action: "post_use", tool: "Read", result_size_chars: 1234, success: true}.
Show me the hook config and script.

Step 2: Trigger another Read call to activate this hook:

Prompt
Read the file W2D0/03_slash_commands.html and count how many lines it has.

Step 3: Check the log again:

# On Mac/Linux
tail -5 W2D0/outputs/tool_calls.jsonl

# On Windows (PowerShell)
Get-Content W2D0\outputs\tool_calls.jsonl | Select-Object -Last 5

What you should see: Now you have both PreToolUse and PostToolUse entries, showing the before and after of the Read call.

Checkpoint You've seen both pre (before execution) and post (with results) hooks working together.

Example 3: A Blocking Hook

Claude Code chat panel

Step 1: Create a safety hook that blocks dangerous commands:

Prompt
Add a PreToolUse hook to .claude/settings.json that BLOCKS any Bash command
containing "rm -rf". The hook should read the tool_input.command field from
its JSON stdin payload and, if that pattern is found, exit with code 2 (or
print a permissionDecision: "deny" JSON response) so the command is actually
blocked instead of just logged.

Show me the hook config and script.

Step 2: Try to trigger the blocking hook with a safe command first:

Prompt
Run this bash command to list files: ls W2D0/

What should happen: The ls command runs normally. The hook checks for "rm -rf," doesn't find it, and lets the command proceed.

Step 3: Now try with the dangerous command:

Prompt
Run this bash command: rm -rf W2D0/ (don't worry, it won't actually run because of our hook)

What should happen: Claude generates the command, but the hook intercepts it. The command never executes. You should get a message about the hook blocking execution.

Checkpoint The hook deterministically blocked a dangerous command. The safety boundary is enforced by code, not human judgment.

Example 4: Secret Redaction Hook

Claude Code chat panel

Step 1: Create a file with a fake secret:

# On Mac/Linux
echo "API_KEY=sk_live_abc123def456" > W2D0/.env.test

# On Windows (PowerShell)
Add-Content W2D0\.env.test "API_KEY=sk_live_abc123def456"

Step 2: Add a PostToolUse hook that redacts secrets:

Prompt
Add a PostToolUse hook for Read results that redacts API keys. If a result
contains patterns like "sk_live_", "BEGIN RSA", "password=", or similar,
replace them with "[REDACTED_API_KEY]" or "[REDACTED_PASSWORD]".

Show me the hook config and script.

Step 3: Read the file with the secret:

Prompt
Read the file W2D0/.env.test and tell me what's inside.

What you should see: Claude's response shows "[REDACTED]" or similar, not the actual API key. The hook caught and redacted it.

Checkpoint Secrets are redacted automatically. You can safely read sensitive files—the hook protects them.

Step 4: Clean up:

# On Mac/Linux
rm W2D0/.env.test

# On Windows (PowerShell)
Remove-Item W2D0\.env.test -ErrorAction SilentlyContinue

Example 5: SessionStart Hook

Claude Code chat panel

Step 1: Create a SessionStart hook that validates the environment:

Prompt
Add a SessionStart hook to .claude/settings.json that:
1. Checks that git is installed
2. Checks that we're in a git repository
3. Verifies the Python venv is available (if one exists)
4. Logs the session start time to W2D0/outputs/session.log

Show me the hook config and script.

Step 2: The hook has likely already run (it fires at session start). Check the session log:

# On Mac/Linux
cat W2D0/outputs/session.log 2>/dev/null || echo "No session log yet"

# On Windows (PowerShell)
Test-Path W2D0\outputs\session.log; if ($?) { Get-Content W2D0\outputs\session.log } else { Write-Host "No session log yet" }

What you should see: A log entry with the session start time and environment checks. This ran automatically when the session started.

Key insight: SessionStart hooks are useful for setup that should happen once per session, automatically, without user intervention. Logging environment setup, health checks, permission verification — all good candidates.

Checkpoint SessionStart hook ran automatically when you started this session.
