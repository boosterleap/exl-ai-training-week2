Slash commands — built-in and custom

The fastest way to repeat a multi-step instruction without retyping it.

Concept: Slash Commands — Built-In and Custom

The Big Picture

A slash command is a shortcut in Claude Code: type /something and Claude does it immediately, without you typing a full prompt.

There are two kinds:

  • Built-in commands — Included with Claude Code. Examples: /help, /compact, /agents, /code-review. These are always available.
  • Custom commands — You create them. They're markdown files that become reusable, parametrized prompts, just like CLAUDE.md is versioned and shared.

Why Custom Commands Matter

Suppose you have a recurring workflow:

Read the git diff for this branch. Summarize it in 3 bullets, mentioning file paths.
Only include changes that aren't test files.

You could type that every time you want a summary. Or you create a custom command /summarize-pr once, commit it to git, and your whole team runs /summarize-pr forever. One more benefit: commands can take arguments, turning /review-pr 142 into a full, structured review.

File Structure and Scoping

Custom commands live here:

  • Project-scoped: .claude/commands/command_name.md — Shared, committed, for the whole team
  • User-scoped: ~/.claude/commands/command_name.md — Personal, in your home directory only

A command file looks simple:

---
name: summarize-pr
description: Summarize the current git branch, excluding tests
arguments: branch
---

Read `git diff origin/main...HEAD` on the branch "$branch".
Summarize the changes in 3-4 bullets. Exclude test files.
Focus on logic changes, not formatting.

The frontmatter (the YAML at the top) defines metadata. The rest is the prompt template. The arguments field declares named positional arguments (a space-separated string or a YAML list of names); each name becomes a $name placeholder in the body—here, $branch is replaced with whatever you pass when you run the command. You can also use $ARGUMENTS for the entire raw argument string, or $1/$2 (shorthand for $ARGUMENTS[0]/$ARGUMENTS[1]) for positional access without naming arguments. Claude Code custom commands do not use {{variable}}-style templating.

Built-In Commands You'll Use

Command What It Does Example
/help Lists all available commands (built-in and custom) /help
/compact Manually triggers context compaction (Topic 07) /compact
/agents Prints a reminder to ask Claude to create/manage subagents, or to edit .claude/agents/ directly (older Claude Code versions opened an interactive list/creation wizard instead) /agents
/mcp Manages MCP server connections (Topic 08) /mcp list
/code-review Runs a security or quality review on pending changes /code-review
/fast Toggles fast mode (faster responses, less reasoning) /fast

Real-World Use Cases

1. Code Review Shortcuts for Your Team

The problem: Your team reviews PRs frequently. Each review follows the same template: "check for edge cases, look for security issues, verify test coverage." Without automation, reviewers paste the same prompt over and over.

The solution: Create a custom command /review-checklist that runs your team's standard review prompt. Commit it to git, and everyone on the team runs it with a real PR number, e.g. /review-checklist 142.

The result: Consistent reviews, saved time, and the prompt lives in your repo (versioned and evolves with your team's standards).

2. Setup and Onboarding for New Team Members

The problem: A new engineer joins. They need to set up their environment, run the test suite, check their access to databases. Instructions are scattered across wikis and Slack.

The solution: Create /onboard command that guides them through every step, including permission checks and environment variable setup.

The result: Onboarding is reliable, repeatable, and automatically updated when your setup process changes.

3. Daily Report Generation

The problem: Your manager asks for a daily standup report: commits made, files changed, tests passed. Same request every day.

The solution: Custom command /daily-report that gathers stats and formats them as a markdown report.

The result: Type /daily-report every morning, get a structured report to paste into your standup.

4. Deployment Safety Checks

The problem: Before deploying, you need to check: are there uncommitted changes? Do tests pass? Is the main branch clean? It's easy to forget one step and break prod.

The solution: Custom command /pre-deploy that runs all checks and refuses to proceed if anything is amiss.

The result: /pre-deploy becomes your deployment gatekeeper. Humans can't skip steps.

5. Bug Triage and Analysis

The problem: A bug report arrives with a stack trace. You need to understand what happened: which code path, what data state, what was the user doing. You manually trace through the logic each time.

The solution: Custom command /analyze-bug <file> <line> that reads the code, traces the logic, and identifies likely root causes.

The result: /analyze-bug my_module.py 42 returns a detailed analysis. Faster debugging, fewer mysteries.

Hands-on Practice: Five Examples

Example 1: Explore Built-In Commands

Claude Code chat panel

Step 1: Type the help command:

/help

What you'll see: A list of all built-in commands (like /help, /compact, /agents) and any custom commands you've created. Each entry includes a description and usage.

Step 2: Try one of the built-in commands:

/agents

What you'll see: On current Claude Code versions, a short reminder to ask Claude to create/manage subagents or edit .claude/agents/ directly (older versions opened an interactive list instead). This will be important in Topic 05.

Step 3: Try another:

/mcp

What you'll see: MCP servers you have connected. This will be important in Topic 08. For now, it shows what's available.

Checkpoint You've discovered the built-in command interface. These are the "meta" commands that manage your Claude Code setup itself.

Example 2: Create a Simple Custom Command

Claude Code chat panel

Step 1: Ask Claude to create a project-scoped custom command:

Prompt
Create a project-scoped custom slash command called /git-status-summary that runs
`git status` and then writes a plain-English summary of what files are staged,
unstaged, and untracked. Show me the exact file you created and its location.

What's happening: Claude creates a markdown file in .claude/commands/git_status_summary.md with frontmatter and a prompt template. This file becomes your command.

Step 2: Verify the file was created:

# On Mac/Linux
ls -la .claude/commands/

# On Windows (PowerShell)
Get-ChildItem .\.claude\commands\

Step 3: Read the file to see its structure:

# On Mac/Linux
cat .claude/commands/git_status_summary.md

# On Windows (PowerShell)
Get-Content .\.claude\commands\git_status_summary.md

What you'll see: A markdown file with YAML frontmatter (name, description) and a prompt template. This is exactly how custom commands work.

Checkpoint The command file exists and has the right structure.

Example 3: Use Your Custom Command

Claude Code chat panel

Step 1: Make a small, harmless edit to any file (to create some git status output):

# On Mac/Linux
echo "# test" >> testfile.txt

# On Windows (PowerShell)
Add-Content testfile.txt "# test"

Step 2: Now run your custom command:

/git-status-summary

What's happening: Claude Code looks up your command definition, interpolates any arguments, and runs the prompt. Claude reads your actual git status and summarizes it.

What you should see: A description of testfile.txt as an untracked file, not generic text — proving the command runs against live state, not a template.

Checkpoint The command output reflects your actual git status, not a generic example.

Step 3: Clean up your test file:

# On Mac/Linux
git checkout -- testfile.txt 2>/dev/null || rm testfile.txt

# On Windows (PowerShell)
git checkout -- testfile.txt -ErrorAction SilentlyContinue; if ($LASTEXITCODE -ne 0) { Remove-Item testfile.txt -ErrorAction SilentlyContinue }

Example 4: Create a Command With Arguments

Claude Code chat panel

Step 1: Ask Claude to create a more advanced command that takes arguments:

Prompt
Create a project-scoped custom command called /explain-function that takes one
argument (a file path) and explains what that file does at a high level, listing
all the main functions/classes and what they do. Show me the file location and
explain how arguments work in custom commands.

Step 2: Verify it was created:

# On Mac/Linux
cat .claude/commands/explain_function.md

# On Windows (PowerShell)
Get-Content .\.claude\commands\explain_function.md

What you'll see: The frontmatter should have an arguments field (e.g. arguments: file_path). The template references it with a $file_path placeholder — or the command may simply use $ARGUMENTS for the whole raw input.

Step 3: Use it with an argument. Pick any Python or JS file in your project:

/explain-function W2D0/capstone/app.py

What's happening: The $file_path (or $ARGUMENTS) placeholder gets replaced with your argument. Claude reads that file and explains it.

Checkpoint The command explanation references the actual file you specified, with real functions/classes from it.

Example 5: Create a User-Scoped Command

Claude Code chat panel

Setup: This command is personal—something you want in every project, not just this one. Create it at user scope.

Step 1: Ask Claude to create a user-scoped command:

Prompt
Create a user-scoped custom command at ~/.claude/commands/my-quick-test.md that
takes no arguments. It should explain what testing frameworks are in use
(by searching package.json, requirements.txt, or similar), then offer to run
the test suite. Show me the exact file path and explain why this is user-scoped,
not project-scoped.

Step 2: Verify it was created in your home directory:

# On Mac/Linux
ls -la ~/.claude/commands/

# On Windows (PowerShell)
Get-ChildItem $env:USERPROFILE\.claude\commands\

Step 3: This command is now available in every project you open. Test it:

/my-quick-test

What's happening: Your user-scoped command loads automatically, just like your user-level CLAUDE.md. It's personal to you, not specific to this project, so it lives in your home directory.

Key difference: A project-scoped command lives in .claude/commands/ (checked into git, shared). A user-scoped command lives in ~/.claude/commands/ (personal, not shared).

Checkpoint The command file exists in your home directory, not in the project. It works in this session and will be available in every other project you open.
