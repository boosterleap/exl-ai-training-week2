Capstone Phase 5 — Human-in-the-Loop, Observability & Evaluation

Every phase so far has been building toward one line in this project's own CLAUDE.md-style ground rules: sensitive or irreversible actions require an explicit human approval step — never auto-send those without one. Phase 5 makes that real — an approval queue and a tamper-evident audit chain — and adds the two things that let you trust the pipeline at all: a structured trace log, and an eval gate with a quality floor instead of a demand for perfection.

Concept: Governance, not just grounding

What counts as "sensitive" here

Phases 2-4 made sure every reply is grounded and every gap is escalated rather than fabricated. But an escalation is itself a disposition someone has to actually act on, and this capstone treats two dispositions as sensitive enough to require a human decision before anything is considered final: an escalation (grounding was unavailable) and a fraud-review case. Everything else — a routine, grounded status or policy reply — doesn't need a human in the loop; it's not the kind of action CLAUDE.md's ground rules are talking about.

An append-only, tamper-evident audit chain

Every decision — queued, approved, rejected, or auto-approved-as-routine — gets one entry in a hash chain (W2D5/snippets/audit_chain.py, reused verbatim): each entry hashes in the previous entry's hash, so editing any past entry breaks verification for everything after it. This is append-only by construction, not by convention.

Observability: a structured trace, not print statements

Phase 2's agent_loop.py now logs every tool call — which tool, what arguments, how long it took, which email it belongs to — to a JSONL trace file. An analyzer (adapted from W2D4/snippets/trace_analyzer.py) surfaces per-tool call counts, average latency, and a repeated-identical-call anomaly detector — the same "is this agent stuck in a loop" signal from Day 1's guardrail topic, now watching a real trace.

An eval gate with a floor, not a demand for perfection

A golden set derived straight from inbound_emails.csv's own ground-truth columns scores every reply on two things: did it escalate exactly the cases with no grounding, and did it cite the right product's policy file. The gate asserts a floor (0.90) — not 100% — because model output varies run to run, and Phase 4 already taught this lesson once with the injection scanner. This phase gives you a second, real instance of the same principle.

Key Learning Objectives

By the end of Phase 5, you will:

  • Build a human-approval queue that gates sensitive dispositions, not every reply
  • Build an append-only audit chain and watch it correctly detect tampering
  • Add structured tool-call tracing to an agent loop you already built, and read a real trace for anomalies
  • Build an eval gate against a golden set derived from your own data's ground truth
  • See, first-hand, why the right target is a quality floor and not a perfect score

"C:\Users\Asus\.venv\Scripts\python.exe" W2D0/capstone/eval_gate.py
Predict first Phase 2 and Phase 3 both ran this exact pipeline and both times every non-gap case cited correctly without over-escalating. Given that this is a live model call and not a fixed script, do you expect every future run to score a perfect 12/12 too?
Debrief No — and the reference run proves it. This run scored 11/12 (0.92), clearing the 0.90 floor but not perfect: LN-006 (a documented education_loan case) correctly cited LOAN-EDU-040_underwriting.md but also escalated it unnecessarily — a real instance of the model being more cautious than strictly required, not a fabrication. That's precisely why the gate asserts a floor instead of exact equality: a single non-deterministic over-caution shouldn't fail a release, but a collapse in grounding accuracy should. Compare this to Phase 4's injection scanner, which scored 21/23 against a fixed, deterministic scanner — this gate's 11/12 comes from live model variance instead, a different source of the same floor-not-perfection lesson.
