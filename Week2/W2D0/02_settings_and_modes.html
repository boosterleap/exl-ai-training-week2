.claude/settings.json & permission modes

Where configuration actually lives, and the real six permission modes — verified straight from claude --help, not paraphrased from memory.

Concept: Settings and Permission Modes

The Big Picture

What it is. Settings are how you configure Claude Code's behavior: which tools are allowed, which get extra prompts, how hooks run, what custom commands exist. They're structured JSON files, unlike CLAUDE.md which is freeform markdown.

Settings come at two scopes, just like CLAUDE.md:

  • User-level (~/.claude/settings.json) — Your personal defaults for every project
  • Project-level (.claude/settings.json) — This project's shared rules, committed to git
  • Project-local (.claude/settings.local.json) — Your personal overrides for this project, gitignored, never shared

Permission Modes: Six Levels From Safe to Fast

A permission mode is your baseline safety/speed tradeoff. Claude Code has exactly six (verified from claude --help):

Mode Safety Level What Happens When to Use
plan 🔒 Highest Claude proposes changes, explains them, but never executes. You click to approve. First time touching unknown code, risky refactors, learning new domains
manual 🔒🔒 Claude asks for permission before any action: editing files, running commands, calling tools. Default for most users. Day-to-day work, balanced safety/speed
acceptEdits 🔒 File edits auto-approve. Other tools (Bash, git, etc.) still ask. Useful for rapid iteration on safe changes. Refactoring your own code, formatting, local debugging
auto ⚠️ Similar to acceptEdits but even more permissive. Fewer prompts overall, but safety policies still apply. High-trust workflows, trusted codebases
dontAsk ⚠️ Stricter, not looser The opposite of permissive: Claude auto-denies anything that isn't already covered by a permissions.allow rule or a built-in read-only command, instead of prompting you. Nothing waits for input — it just gets refused. Locked-down CI pipelines and scripts where you've pre-declared exactly what's allowed
bypassPermissions 🟡 Low No prompts, no checks — everything runs immediately. This is a recommendation, not an enforced sandbox: Claude Code itself doesn't cut off internet or tool access in this mode, so only use it somewhere isolated (a container/VM with no network) where a mistake can't reach anything you care about. CI/CD, testing, demos — in isolated containers/VMs only

Naming note: the mode most people start in is labeled Manual in the CLI, in claude --help, and in the VS Code/JetBrains/desktop UIs, but its underlying config value is default — Claude Code also accepts manual as a typed alias for it, so both spellings work in --permission-mode and in defaultMode.

How Permissions Refine the Mode

A permission mode is just the baseline. Within that mode, you can set specific rules for individual tools. Three rule types:

  • allow — This tool doesn't prompt. Auto-approved within the current mode.
  • ask — Always ask before using this tool, even in looser modes.
  • deny — Never allow this tool, period.

Example: If you're in manual mode but add "allow": ["Edit"], then file edits auto-approve while everything else still asks.

Settings File Structure

A minimal settings.json looks like:

{
  "permissions": {
    "defaultMode": "manual",
    "allow": ["Read", "Glob", "Edit"],
    "ask": ["Bash"],
    "deny": ["PowerShell"]
  },
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [{ "type": "command", "command": "npm run lint" }]
      }
    ]
  }
}

Note: the permission mode lives nested under permissions.defaultMode, not as a top-level permissionMode key. Hooks are keyed by lifecycle event name (PreToolUse, PostToolUse, SessionStart, Stop, and others) rather than by names like beforeWrite/beforePush. And there's no customCommands key at all — custom slash commands are separate files, one per command, under .claude/commands/<name>.md (or, in current Claude Code, a folder-based skill at .claude/skills/<name>/SKILL.md — see the skills topic for that distinction).

Debugging: claude doctor and --safe-mode

When something behaves unexpectedly:

  • claude doctor — Checks your setup: are custom commands registered? Are hooks syntactically valid? Are MCP servers running? Reports any issues.
  • --safe-mode — Temporarily disables all customizations (CLAUDE.md, hooks, skills, commands, agents) so you can test whether the issue is your config or something else.

Real-World Use Cases

1. Protecting Sensitive Files From Accidental Edits

The problem: You have secrets, config files, and database schemas that should never be edited in Claude Code sessions.

The solution: In .claude/settings.json (committed to git):

{
  "permissions": {
    "deny": ["Edit"],
    "denyPatterns": ["**/.env*", "**/secrets/**", "database/schema.sql"]
  }
}

The result: Claude can read these files but cannot edit them. If it tries to edit .env, Claude Code refuses and warns you.

2. Fast Iteration for Trusted Refactors

The problem: You're refactoring your own code in a small module. You know the changes are safe. Asking for permission on every edit slows you down.

The solution: Temporarily switch to acceptEdits mode:

claude --permission-mode acceptEdits

Or, in settings.local.json (just for this project, this session):

{
  "permissions": {
    "defaultMode": "acceptEdits"
  }
}

The result: File edits auto-approve. Bash commands still ask. You get speed for safe operations, safety for dangerous ones.

3. Requiring Approval For Risky Tools

The problem: You're in auto mode (fast, few prompts). But you want git push and Bash to always ask before running.

The solution: In .claude/settings.json:

{
  "permissions": {
    "defaultMode": "auto",
    "ask": ["Bash", "RemoteTrigger"]
  }
}

The result: Fast mode for file edits, but any Bash or remote operations still require your approval.

4. Enforcing Code Quality Gates

The problem: You want Claude to suggest changes, but also to run your linter and tests before finalizing them.

The solution: In .claude/settings.json:

{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [{ "type": "command", "command": "npm run lint -- --fix" }]
      }
    ],
    "PreToolUse": [
      {
        "matcher": "Bash(git push*)",
        "hooks": [{ "type": "command", "command": "npm test" }]
      }
    ]
  }
}

(Hooks are keyed by lifecycle event — PreToolUse runs before a matching tool call and can block it by exiting non-zero; PostToolUse runs after. There's no beforeWrite/beforePush/onFailure shorthand in the real schema — matching and blocking both happen through the matcher pattern and the hook script's exit code.)

The result: Before saving a file, linting runs automatically. Before pushing, tests must pass or the push blocks. Quality gates happen without you asking.

5. Learning Mode: Maximum Safety While Exploring Unknown Code

The problem: You're exploring a large, unfamiliar codebase. You want to ask questions and have Claude propose solutions, but absolutely no edits until you review carefully.

The solution: Start the session in plan mode:

claude --permission-mode plan

The result: Claude analyzes, proposes, explains — but never edits. You review everything before clicking "approve" in plan proposals.

Hands-on Practice: Five Examples

Example 1: Examine Your Current Settings

Terminal/PowerShell

Step 1: Check your user-level settings:

# On Mac/Linux
cat ~/.claude/settings.json 2>&1 || echo "no user-level settings yet"

# On Windows (PowerShell)
Test-Path $env:USERPROFILE\.claude\settings.json; if ($?) { Get-Content $env:USERPROFILE\.claude\settings.json } else { Write-Host "no user-level settings yet" }

Step 2: Check this project's settings:

# On Mac/Linux
cat ./.claude/settings.json 2>&1 || echo "none yet"
cat ./.claude/settings.local.json 2>&1 || echo "none yet"

# On Windows (PowerShell)
Test-Path .\.claude\settings.json; if ($?) { Get-Content .\.claude\settings.json } else { Write-Host "none yet" }
Test-Path .\.claude\settings.local.json; if ($?) { Get-Content .\.claude\settings.local.json } else { Write-Host "none yet" }

What's happening: Settings files are optional. Many projects start without them. If they don't exist, that's fine — Claude Code uses built-in defaults.

Checkpoint You've identified which settings files (if any) exist at each scope.

Example 2: Try Plan Mode

Claude Code chat panel

Step 1: Switch to plan mode. Use the mode picker in your Claude Code UI, or run:

claude --permission-mode plan

Step 2: Ask Claude to edit something:

Prompt
Add a one-line comment to the top of the CLAUDE.md file: "# Updated on [today's date]"

What's happening: Claude proposes the change in detail, showing you exactly what it will add. But it doesn't actually write the file. You get to review before approving.

Checkpoint Claude should show you a plan with the proposed change, but the file should NOT be modified yet.

Step 3: Now switch back to your normal mode (usually manual) and ask again:

Prompt
Add the same comment to CLAUDE.md: "# Updated on [today's date]"

What's happening: This time, Claude either edits immediately (if you're in a fast mode like acceptEdits) or asks for your approval. Either way, the file gets modified.

Checkpoint The CLAUDE.md file now has the comment added. You've seen the difference between plan mode (proposes only) and your normal mode (proposes and executes).

Example 3: Create a Project-Local Settings File

Claude Code chat panel

Create a .claude/settings.local.json file with safe defaults for your personal experiments:

Prompt
Create a file at .claude/settings.local.json with this content:

{
  "permissions": {
    "defaultMode": "acceptEdits",
    "ask": ["Bash", "RemoteTrigger"]
  }
}

This means: auto-approve file edits, but ask before running any bash commands or remote triggers.

What's happening: You've created a personal settings override for this project. It's in .gitignore, so it won't be committed. Your team members can have different settings without conflicts.

Step 2: Verify the file was created:

# On Mac/Linux
cat ./.claude/settings.local.json

# On Windows (PowerShell)
Get-Content .\.claude\settings.local.json
Checkpoint The file exists and has the JSON structure you specified.

Step 3: Now try editing a file (should auto-approve) and running a bash command (should ask):

Prompt
1. Create a new file called test.txt with the content "Hello World"
2. Run the command: ls -la test.txt

What's happening: The file edit should happen without asking. The bash command should prompt you for permission. This proves your settings are being applied.

Checkpoint File edit auto-approved, bash command asked for permission. Your settings.local.json is working.

Example 4: Run claude doctor

Terminal/PowerShell

Step 1: Run the diagnostic tool:

claude doctor

What it checks:

  • Is Claude Code installed and on your PATH?
  • Are your CLAUDE.md files readable?
  • Are your settings.json files valid JSON?
  • Are custom commands registered and executable?
  • Are hooks syntactically correct?
  • Are MCP servers running (if configured)?

What's happening: This tool validates your entire setup. If something is misconfigured, it tells you exactly what and where.

Checkpoint claude doctor completes. If it reports any issues, you now know where to look to fix them.

Example 5: Safe Mode for Troubleshooting

Claude Code chat panel

Step 1: Start a session in safe mode:

claude --safe-mode

Step 2: Try a command that uses your customizations:

Prompt
List any files named test.* in the current directory.

What's happening: Safe mode disables CLAUDE.md, hooks, custom commands, and agents. If your command works in safe mode but fails normally, the issue is your config, not Claude Code itself.

Checkpoint You've confirmed your setup works in safe mode. If a feature doesn't work outside safe mode, you know to check your CLAUDE.md or settings files.

Step 3: Exit safe mode and return to normal operation:

claude

Tip: Safe mode is your diagnostic tool. When something seems broken, always try safe mode first to isolate whether the issue is your customization or Claude Code itself.
