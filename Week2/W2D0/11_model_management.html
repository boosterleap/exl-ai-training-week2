Model management — switching, fallback, and cost visibility

Concept: Model Selection and Cost Management

The Big Picture

Claude Code lets you choose which Claude model runs your session. Different models have different speed/cost tradeoffs:

  • Claude Haiku (fastest, cheapest): Best for quick tasks, straightforward coding, simple analysis. Lower cost, faster response.
  • Claude Sonnet (balanced): Default for most work. Good reasoning, fast enough.
  • Claude Opus (most capable, slower, most expensive): For hard problems, complex reasoning, design decisions. Slower, costs more.

Where to Set the Model

  • ~/.claude/settings.json: Default model for all sessions (the "model" field)
  • claude --model opus: Override for one session
  • /model: Switch mid-session — run it with a name/alias to switch immediately, or with no argument to open an interactive picker. This is a built-in Claude Code command, not something that depends on your IDE.

Fallback and Reliability

--fallback-model specifies one or more alternate models to try if your primary model is overloaded, unavailable, or returns another non-retryable server error (it does not kick in for auth, billing, rate-limit, or request-size errors):

claude --model opus --fallback-model sonnet

If Opus is overloaded or unavailable, the session automatically retries with Sonnet. The fallback only applies for the current turn — your next message tries Opus again. (You can also chain multiple fallbacks, comma-separated, e.g. --fallback-model sonnet,haiku, and persist a chain across sessions with the fallbackModel array in settings.json.)

Cost Visibility

Always check token usage:

  • At the end of a session, Claude reports tokens used and estimated cost
  • Long sessions with complex tasks can add up
  • Cheaper models (Haiku) are fine for routine coding; splurge on Opus for design questions

Real-World Use Cases

1. Cost Optimization for Routine Tasks

The problem: You use Opus for everything. Your bill is high, but most tasks are simple code changes that don't need Opus's depth.

The solution: Switch to Haiku for routine edits. Use Opus only for architecture and design decisions.

The result: 50-70% cost reduction while maintaining quality for complex tasks.

2. Hard Design Problems

The problem: A tough architectural question. Cheaper models give surface-level answers. You need deep reasoning.

The solution: `claude --model opus` for that specific session. Spend more where it matters.

The result: Better architectural decisions, faster consensus.

3. Reliability in Production Systems

The problem: A critical agent must stay responsive, even if the primary API is slow.

The solution: `--fallback-model` ensures automatic retry on a backup model if needed.

The result: More reliable service. No manual intervention needed for model unavailability.

4. Learning and Experimentation

The problem: You're exploring an unfamiliar domain. Cheaper models help you learn without big costs.

The solution: Start with Haiku for learning. Graduate to better models when you have more context.

The result: Cheaper exploration. Less waste on "what's the right direction?" questions.

5. Batch Processing

The problem: You need to process 1000 small, similar tasks (e.g., analyze logs, summarize customer feedback).

The solution: Haiku or Sonnet for batch work. Save Opus for exceptions needing deeper reasoning.

The result: Massive cost savings on repetitive work.

Hands-on Practice: Three Examples

Example 1: Check Current Model Default

Terminal/PowerShell

Step 1: Check your settings:

# On Mac/Linux
cat ~/.claude/settings.json | grep -i model || echo "no explicit model set"

# On Windows (PowerShell)
Select-String -Path $env:USERPROFILE\.claude\settings.json -Pattern "model" -ErrorAction SilentlyContinue || Write-Host "no model set"
Checkpoint You know what your current default model is (or that no explicit default is set).

Example 2: Override Model for a Session

Claude Code chat panel

Step 1: Ask Claude what model it's using:

Prompt
What Claude model are you running right now? (This is metadata, not a task.)

Step 2: Try a model override via your UI's model picker or settings (specific method depends on your IDE integration).

Checkpoint You've switched models and confirmed the change.

Example 3: Monitor Token/Cost Usage

Claude Code chat panel

Step 1: Ask Claude about token usage in this session:

Prompt
Roughly how many tokens have been used in this W2D0 session so far?
Estimate the cost at current model rates.

What you'll see: Estimate of tokens and cost. This helps you understand the budget impact of long sessions or expensive models.

Checkpoint You're aware of cost. Use this knowledge to choose Haiku for cheap routine work and Opus for hard problems.

Prompt
Here's a deliberately underspecified request: "make the config better."
Without asking me a clarifying question, tell me what you'd actually do
and why. (Run this once per model you're comparing.)
Checkpoint Compare: did the faster model barrel ahead with an assumption, while the deeper one flagged the ambiguity or asked first? Neither is universally "better" — it's a task-fit decision.
