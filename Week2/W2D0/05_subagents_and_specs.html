Subagents — defining, dispatching, and the spec format

You've already used subagents throughout Week 2 (the Agent tool). This topic is how to define your own, not just use the built-in ones.

Concept

A subagent is a named, reusable specialist with its own isolated context — you dispatch it with a specific brief, it does its work independently (possibly reading many files or running many commands), and only a distilled result comes back to your main session. You define one as a markdown file with frontmatter — the "spec" — describing its name, when to use it, and what tools it's allowed.

  • Why isolation is the whole point. A subagent doing a long, detail-heavy investigation would otherwise flood your main session's context with intermediate noise — this is Day 2's exact isolation-spectrum argument, now from the defining side instead of the using side.
  • The spec format matters because it's how Claude Code decides when to reach for a subagent automatically. A vague description gets it invoked at the wrong times (or never); a precise one — including a few concrete example situations — gets it invoked exactly when it should be.
  • Project- vs. user-scoped, again. A subagent tightly coupled to this repo's conventions belongs at project scope; a general-purpose one (e.g. "code reviewer") belongs at user scope so it follows you everywhere.

Hands-on

1See what's already defined
Claude Code chat panel or CLI 
/agents

or, non-interactively:

claude agents --json 2>&1 | head -c 400
2Define your own subagent
Prompt
Define a project-scoped subagent called "doc-freshness-checker" whose job
is: given a markdown file, check whether it references any file paths that
no longer exist in the repo, and report exactly which ones are stale. Write
the spec file with a clear description of when you should be invoked
(including one concrete example), and tell me where you put it.
3Dispatch it for real
Prompt
Dispatch doc-freshness-checker on this file: W2D0/00_orientation.html.
Show me exactly what it reports.
Checkpoint You should see a real, isolated dispatch (not just Claude Code doing the check itself in-context) and a distilled report back — the same shape as every subagent dispatch you've watched all through Week 2, except this time you wrote the spec.
4Probe the isolation boundary
Prompt
Dispatch doc-freshness-checker again, and ask it (as part of the brief):
"what was the first thing we discussed in this W2D0 session, from memory
only?" Report exactly what it says.

It shouldn't know — the same isolation test from Week 2 Day 2, now run against a subagent you defined yourself.
