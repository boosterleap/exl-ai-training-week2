Topic 01 · The agentic loop, in depth

1Perceive → reason → act → observe~40 min

Concept. An agent isn't "a prompt that's a bit smarter" — it's a small distributed system where the LLM itself is the planner and the executor: it decides what to look up, does the looking-up (via tools), reads what came back, and decides what's next. That loop — perceive, reason, act, observe — repeats until the model decides it's done.

  • Why "distributed system," specifically. Each act/observe pair is a network or filesystem round-trip with its own latency and its own chance of partial failure (a tool can time out, return an error, or return something the model misreads) — reasoning has to account for that, the same way a distributed backend has to handle a flaky downstream service.
  • What a one-shot completion loses. A single "perceive → reason → output text" call (no act/observe) can only answer from what's already in the prompt. The moment it needs a fact it doesn't have, a one-shot call either admits it can't help or — worse — guesses. The loop exists specifically to let the model go get the fact instead of guessing it.
  • How the loop knows when to stop. There's no fixed step count. The model itself decides "I have enough to answer" and emits a final text response with no further tool call. That termination decision is itself part of what you're evaluating when you watch a transcript.
  • "Turn" vs "loop." What you call one message to Claude Code can contain many internal act/observe cycles before you see a reply — the loop runs inside a single turn, not once per turn.
Predict, then verify Before running anything: open data/insurance/fnol_emails.csv and read row CLN-001 (Jennifer Garcia, claim CLM-424063). If you asked an assistant to "handle this email," what would it need to look up before it could reply? Write down 2–3 things it needs to know that aren't in the email itself. Then also predict: if you forbade it from looking anything up, what would it do instead?

Topic 02 · Reasoning & planning patterns

2ReAct, plan-and-execute, reflection, tree-of-thought~45 min

Concept. There's more than one way for a model to organize its reasoning. ReAct interleaves one thought with one action, repeatedly. Plan-and-execute writes the whole plan first, then runs it. Reflection produces a draft, critiques it, and revises. Tree-of-thought explores multiple branches and picks the best one — powerful, but the most expensive, so it's used sparingly. 2026 "thinking" models can also do extended, visible reasoning before responding — a different lever from which pattern you prompt for.

  • Cost/latency ordering. Roughly cheapest-to-priciest: ReAct (one small step at a time, cheap per step but can take many steps) → plan-and-execute (one planning cost up front, then cheaper execution) → reflection (pay for a draft and a critique pass) → tree-of-thought (pay for multiple parallel branches, discard most of them).
  • When to reach for which. ReAct suits tool-heavy, exploratory tasks where the next step genuinely depends on what came back. Plan-and-execute suits well-understood multi-step workflows where the steps are knowable in advance. Reflection suits anything where correctness matters more than speed (a coverage citation, a legal-sensitive statement). Tree-of-thought suits genuinely ambiguous, high-stakes single decisions — not routine triage.
  • Extended thinking is orthogonal. A model can "think harder" (more internal deliberation before any output) independent of which of the four patterns you prompted for — it's a dial on depth, not a fifth pattern.
  • Production systems blend these. A real triage agent might use ReAct to gather facts, then a short reflection pass just before sending a customer-facing reply — you rarely commit to exactly one pattern for an entire task.

Topic 03 · Tools as contracts

3JSON-schema, validation, idempotency, budgets~40 min

Concept. A tool call is a contract, not a suggestion: the model must supply arguments matching a schema, the tool validates them, and the tool's output is itself validated before the model trusts it. A well-designed tool is also idempotent — calling it twice with the same input causes no extra side effect — and carries an explicit time/cost budget so one runaway call can't blow the whole session.

  • Read tools vs. write tools need different contracts. A read-only lookup only needs input validation and a "not found" path. A write tool (approve a payment, send an email) additionally needs idempotency — typically an idempotency key so a retried call doesn't double-charge or double-send — and usually a human approval gate before it fires.
  • What a validation failure looks like in practice. If the model supplies a malformed argument (wrong type, missing field), the tool should reject it with a clear error before touching any data — that error becomes part of the model's next reasoning step, not a silent failure.
  • Budgets are a code-level check, not a polite request. "Don't call this more than 3 times" only works reliably if your code counts calls and refuses the 4th — not if it's just a line in the prompt.

Design together, out loud, before any code exists — read tool. Claude Code chat panel — this is a design conversation, not a build yet (the build happens this afternoon in W2D1PM):

Topic 04 · Memory, layered

4Working context, summaries, artifacts, long-term preferences~40 min

Concept. "Memory" for an agent isn't one thing and it isn't just a vector database. It's layered: working context (this turn), summaries (compacted history once context fills up), artifacts (files written to disk — including CLAUDE.md itself), and long-term preferences (true across sessions). A long, unmanaged context also suffers the lost-in-the-middle effect: facts buried in the middle of a huge context get under-weighted by the model, even though they're technically "in there."

  • What triggers compaction. As a session's context approaches its limit, older turns get automatically summarized so the session can keep going — this is automatic, not something you request, and it's lossy by nature: detail is traded for space.
  • Artifacts are compaction-proof; working context isn't. A fact that only lives in turn 3 of a long conversation can get summarized away by turn 40. The same fact written into CLAUDE.md gets re-read fresh at the start of every new session, regardless of how long any single conversation ran.
  • Session memory vs. project memory. A session's working context is private to that one conversation. CLAUDE.md is project-level — every session, including brand-new ones, starts by reading it. That distinction matters again this afternoon (Day 1 PM Topic 04) when you resume a specific session by ID.

Topic 05 · Agent vs pipeline

5When judgment earns its cost, and when it doesn't~35 min

Concept. Not every email needs an agent. If the path is fully predictable — "shipment delivered, no exceptions, customer wants a confirmation" — a hardcoded pipeline is cheaper, faster, and fully deterministic. An agent earns its extra cost only when the next step genuinely depends on judgment the code can't pre-script.

  • The cost math. A hardcoded pipeline, once written, costs zero model calls to run. An agent loop costs one or more model calls every single time, for every email. That's the trade you're actually making — not "agents are smarter," but "agents cost recurring money and pipelines cost one-time engineering."
  • The hybrid pattern is what production systems actually do. A deterministic pre-filter routes the easy, predictable majority of cases straight to a canned or templated response, and only hands the genuinely ambiguous minority to the agent. This is usually the right answer, not "pick one."
  • The trap to avoid. Routing everything to an agent "to be safe" quietly turns a cheap, instant operation into a slow, costly one with no accuracy benefit — the model will just reach the same obvious conclusion the pipeline would have, more slowly and less predictably.

Topic 06 · Failure modes & guardrails (intro)

6Hallucinated calls, loops, runaway cost — deterministic control points~30 min

Concept. Left unchecked, an agent loop can hallucinate a tool call, loop without making progress, or simply run up cost. The fix isn't "ask the model to be careful" — it's deterministic control points in your own code: budget checks, evidence checks, and approval gates that don't depend on the model choosing to stop.

  • Budget guardrail, concretely. A hard cap on tool calls or elapsed time per task, enforced by counting in code — once hit, the loop stops and reports "budget exceeded," it doesn't ask the model nicely to wrap up.
  • Loop-detection guardrail. The same tool called repeatedly with the same (or near-identical) arguments with no new information is a sign of a stuck loop, not progress — worth detecting and halting explicitly.
  • Evidence guardrail. No matching record/document found means the answer must say so — this is what you're about to test directly below.
  • Approval guardrail. Anything irreversible (a payment, a policy change, a sent customer email) waits for an explicit human decision — this is Day 1 PM's Topic 05 in practice.

What should a well-guarded assistant do when asked to explain this claimant's coverage? Separately predict: what should happen if you ask about a claim_id that doesn't exist at all — is that the same failure mode, or a different one?
