Capstone Phase 3 — Multi-Agent Systems & MCP

Phase 2 built one agent that does everything: read the email, call two tools, draft a reply. Phase 3 splits that into two roles — a cheap intake/classifier subagent and the underwriting subagent from Phase 2 — coordinated by an orchestrator, and moves the two grounding tools off in-process function calls onto a real network MCP server, the same upgrade path Day 2 PM takes with the insurance thread's claims lookup.

Concept: Splitting roles, and a real network MCP server

Why split the single agent into two subagents

Phase 2's agent did classification and grounded drafting in one loop. That's fine at 12 emails, but it conflates two different jobs with two different cost/latency profiles: classification is a single cheap structured call (which category, which Loan_ID), while grounded drafting is a multi-turn tool-use loop. Splitting them lets an orchestrator route work — and lets you see, concretely, where each role succeeds or fails independently.

From in-process import to a real MCP server

Phase 2 called get_loan_record/search_policy as plain Python functions in the same process. Phase 3 exposes the same two functions over Streamable HTTP — a standalone service on its own port, the same pattern as W2D2/my_claims_network_server.py. This is the actual Day 2 PM upgrade: Day 1 wires an MCP server Claude Code launches itself (stdio, in-process); Day 2 PM makes it a real network service other clients — including a second machine — could call.

A second safety layer, independent of classification

The underwriting subagent's grounding check (grounding_available) doesn't depend on the intake subagent getting the category right. Even if intake mislabels an email's intent, the underwriting subagent still looks up the actual Loan_ID, still checks whether a policy document exists for that product, and still escalates on gold_loan regardless of what category label got attached upstream. That independence is deliberate — worth confirming with real, imperfect classifier output rather than a hand-picked clean run.

Key Learning Objectives

By the end of Phase 3, you will:

  • Split a single agent into two subagents with distinct responsibilities and prompts
  • Build an orchestrator that routes between them and records both outputs
  • Move a tool surface from in-process calls to a real Streamable HTTP MCP server
  • Verify, with a genuinely imperfect classifier, that a downstream safety check doesn't depend on an upstream classification being correct

Then start it for real in a separate terminal and confirm it's actually listening on the network (not just self-check):

"C:\Users\Asus\.venv\Scripts\python.exe" W2D0/capstone/mcp_loan_server.py
# separate terminal:
curl -i http://127.0.0.1:8770/mcp

A bare curl GET isn't a real MCP client, so expect 406 Not Acceptable rather than a 404/connection-refused — that response code is itself the confirmation: something real is listening and enforcing the Streamable HTTP protocol's content-negotiation rules, not silently accepting anything.

To exercise it as a real client, point Claude Code's own .mcp.json at it (same shape as this repo's root .mcp.json, which already configures the insurance-thread policy-search server) and ask Claude Code directly to look up a loan through the tool — that live round trip through the actual MCP protocol is the equivalent of Day 2 PM's manual verification step.

"C:\Users\Asus\.venv\Scripts\python.exe" W2D0/capstone/multiagent.py
Debrief The verified reference run scored 10/12 on category — it missed exactly those two ambiguous cases (LN-005 called status_inquiry instead of rate_query; LN-012 called status_inquiry instead of fraud_escalation, since the email body genuinely never says "fraud"). Both misses are defensible given what's actually in the email text — the ground-truth label encodes internal knowledge the customer's own words don't carry. The important result is what didn't break: the underwriting subagent still correctly escalated all three gold_loan/gap cases (LN-004, LN-005, LN-012) regardless of the classifier's label, because its escalation check runs off grounding_available, not off the intake category.
